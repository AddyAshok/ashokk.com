Method Security: @PreAuthorize, @PostAuthorize and Custom Permission Rules

URL rules are coarse. Method security puts the rule next to the business method, has access to method arguments and return values, and also protects calls that do not come through HTTP (jobs, messages).

Enable and use

@Configuration
@EnableMethodSecurity           // Spring Security 6: prePostEnabled = true by default. Also: securedEnabled, jsr250Enabled
public class MethodSecurityConfig { }

@Service
public class DocumentService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteAll() { }

    @PreAuthorize("hasAuthority('documents:read') and #ownerId == authentication.name")     // uses the argument
    public List<Document> findByOwner(String ownerId) { return List.of(); }

    @PostAuthorize("returnObject.owner == authentication.name or hasRole('ADMIN')")        // checks the RESULT
    public Document get(Long id) { return repository.findById(id).orElseThrow(); }

    @PreFilter("filterObject.owner == authentication.name")                                // filters an input collection
    public void saveAll(List<Document> documents) { }

    @PostFilter("filterObject.owner == authentication.name")                               // filters the returned collection (loads everything first!)
    public List<Document> findAll() { return repository.findAll(); }
}

@PreAuthorizeBefore the method runsArguments (#name), authentication, roles, beans
@PostAuthorizeAfter the method, before returningreturnObject
@PreFilter / @PostFilterRemove elements from a collection argument or resultfilterObject
@Secured({"ROLE_ADMIN"})BeforeOnly role names, no SpEL
@RolesAllowed (JSR-250)BeforeRole names, standard annotation

Internal workflow

caller ─► Spring AOP proxy of DocumentService
              └─ AuthorizationManagerBeforeMethodInterceptor   (from @EnableMethodSecurity)
                     1. read @PreAuthorize expression
                     2. build a MethodSecurityExpressionRoot: authentication, hasRole(), hasAuthority(), arguments, beans
                     3. evaluate the SpEL expression
                     4. false ─► AccessDeniedException (403)      true ─► call the real method
              └─ (after) AuthorizationManagerAfterMethodInterceptor for @PostAuthorize with returnObject

Because it uses AOP proxies, the same limits apply as for @Transactional: a call from another method in the SAME class is not checked (self invocation), private methods are not checked, and the bean must be created by Spring. Put security annotations on the public methods of beans that are called from outside.

Custom permission logic as a bean

@Component("perm")
public class PermissionService {
    private final DocumentRepository documents;
    public PermissionService(DocumentRepository documents) { this.documents = documents; }

    public boolean canEdit(Long documentId, Authentication auth) {
        return documents.findById(documentId)
                .map(d -> d.getOwner().equals(auth.getName()) || auth.getAuthorities().stream().anyMatch(a -> a.getAuthority().equals("ROLE_ADMIN")))
                .orElse(false);
    }
}

@Service
public class DocumentEditService {
    @PreAuthorize("@perm.canEdit(#id, authentication)")        // call a Spring bean from the expression
    public void update(Long id, String text) { }
}

Meta-annotations: readable rules

@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@PreAuthorize("hasRole('ADMIN')")
public @interface IsAdmin { }

@IsAdmin
public void deleteUser(Long id) { }

Best practice: filter in the query, not after

// BAD: loads all documents, then removes the ones the user may not see (slow, may leak through logs)
@PostFilter("filterObject.owner == authentication.name")
List<Document> findAll();

// GOOD: the database only returns allowed rows
@Query("select d from Document d where d.owner = ?#{authentication.name}")     // needs SecurityEvaluationContextExtension
List<Document> findMine();
// or pass the username explicitly: findByOwner(String owner) and call it with the current user

Common mistake: Adding @PreAuthorize to a private method or calling the secured method from within the same class. The proxy is bypassed and the check silently does not run. Test 403 behavior with an integration test.

Interview questions

URL security or method security?

Use both. URL rules give a coarse first barrier. Method security enforces fine-grained rules close to the business logic and also protects non-HTTP entry points.

Why is my @PreAuthorize ignored?

Usually @EnableMethodSecurity is missing, the call is a self invocation, the method is private or final, or the bean is not created by Spring.

What is the difference between @Secured and @PreAuthorize?

@Secured accepts only role names. @PreAuthorize accepts full SpEL expressions with arguments, beans and complex logic.
