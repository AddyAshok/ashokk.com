Authorization Internals: AuthorizationFilter, AuthorizationManager and Rules

Authorization decides what an authenticated user may do. This page shows how the URL based check works inside, how roles and authorities differ, role hierarchies, and how to write your own AuthorizationManager for rules such as ownership or time of day.

Workflow of a URL access check

AuthorizationFilter.doFilter(request)
  1. Supplier<Authentication> auth = () -> SecurityContextHolder.getContext().getAuthentication()   (lazy)
  2. RequestMatcherDelegatingAuthorizationManager: find the FIRST rule whose matcher matches the request
       /public/**   -> permitAll        (AuthorizationManagers: always granted)
       /admin/**    -> hasRole("ADMIN") -> AuthorityAuthorizationManager
       anyRequest   -> authenticated()  -> AuthenticatedAuthorizationManager
  3. manager.check(auth, request)  ──►  AuthorizationDecision(granted true/false)
  4. granted     ─► chain.doFilter (continue to the controller)
     not granted ─► AccessDeniedException ─► ExceptionTranslationFilter:
                        anonymous user  ─► start authentication (401 or redirect to login)
                        logged in user  ─► AccessDeniedHandler ─► 403

http.authorizeHttpRequests(auth -> auth
    .requestMatchers(HttpMethod.GET,    "/api/orders/**").hasAuthority("orders:read")
    .requestMatchers(HttpMethod.POST,   "/api/orders/**").hasAuthority("orders:write")
    .requestMatchers(HttpMethod.DELETE, "/api/orders/**").hasAnyRole("ADMIN", "MANAGER")
    .requestMatchers("/api/reports/**").access(AuthorizationManagers.allOf(
            AuthorityAuthorizationManager.hasRole("MANAGER"),
            AuthorityAuthorizationManager.hasAuthority("reports:view")))
    .requestMatchers("/internal/**").access(new WebExpressionAuthorizationManager("hasIpAddress('10.0.0.0/8')"))
    .anyRequest().denyAll());

Role hierarchy

@Bean
RoleHierarchy roleHierarchy() {
    return RoleHierarchyImpl.fromHierarchy("ROLE_ADMIN > ROLE_MANAGER\nROLE_MANAGER > ROLE_USER");   // ADMIN also has MANAGER and USER rights
}
// Spring Security 6.3 and older: RoleHierarchyImpl h = new RoleHierarchyImpl(); h.setHierarchy("ROLE_ADMIN > ROLE_MANAGER > ROLE_USER");

Custom AuthorizationManager: owner or admin

@Component
public class OrderOwnerAuthorizationManager implements AuthorizationManager<RequestAuthorizationContext> {

    private final OrderRepository orders;
    public OrderOwnerAuthorizationManager(OrderRepository orders) { this.orders = orders; }

    @Override
    public AuthorizationDecision check(Supplier<Authentication> authentication, RequestAuthorizationContext context) {
        Authentication auth = authentication.get();
        if (auth == null || !auth.isAuthenticated()) return new AuthorizationDecision(false);
        boolean admin = auth.getAuthorities().stream().anyMatch(a -> a.getAuthority().equals("ROLE_ADMIN"));
        if (admin) return new AuthorizationDecision(true);
        Long orderId = Long.valueOf(context.getVariables().get("id"));       // from the URL template
        boolean owner = orders.findById(orderId).map(o -> o.getOwner().equals(auth.getName())).orElse(false);
        return new AuthorizationDecision(owner);
    }
}

// use:  .requestMatchers("/api/orders/{id}").access(orderOwnerAuthorizationManager)

Rules for safe authorization

  • Default deny: finish with anyRequest().denyAll() (or authenticated() for simple apps).
  • Do access control on the SERVER for every request. Hiding a button in the UI is not security.
  • Check ownership, not only roles. This is the classic Broken Object Level Authorization (BOLA / IDOR) bug: user 5 can read /orders/6 because only 'is logged in' was checked.
  • Use least privilege: give each role only what it needs.
  • Keep URL rules simple, and put fine-grained business rules into method security next to the data access.

Common mistake: Checking only that the user is logged in and then loading an object by the id from the URL. Any logged-in user can read any record by changing the number (IDOR). Always verify ownership or permission for the concrete object.

Interview questions

hasRole('ADMIN') or hasAuthority('ROLE_ADMIN')?

They are the same. hasRole adds the ROLE_ prefix. Choose one convention and use it everywhere.

Why do I get 403 with the role name ADMIN in the database?

The authority must be ROLE_ADMIN when you use hasRole('ADMIN'). Map database roles to authorities with the prefix.

What is BOLA or IDOR?

Broken object level authorization: the server checks who you are but not whether you may access this specific object. It is the number one API security problem.
