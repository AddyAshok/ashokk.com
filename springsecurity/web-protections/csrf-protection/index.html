CSRF Protection in Depth

CSRF makes a victim's browser send an authenticated request to your site without the victim knowing. Spring Security protects against it by default with a token. You must know when this protection is needed, how it works internally, and how to configure it for single page apps.

The attack

1. You are logged in to bank.com (browser has the session cookie)
2. You open evil.com in another tab. It contains:
      <form action="https://bank.com/transfer" method="POST"> <input name="to" value="attacker"> <input name="amount" value="5000"> </form>
      <script>document.forms[0].submit()</script>
3. Your browser sends POST /transfer to bank.com AND automatically adds your session cookie
4. bank.com sees a valid session and transfers the money.
The attacker cannot READ the response, but the state change happened.

The defense: a token the attacker cannot know

GET /transfer-form           ─► server creates a random CSRF token, stores it in the session, puts it in the HTML form (hidden field _csrf)
POST /transfer  _csrf=8f3c...   ─► CsrfFilter compares the token from the request with the token stored on the server
      equal ─► continue          different or missing ─► 403 Forbidden (InvalidCsrfTokenException / MissingCsrfTokenException)
evil.com cannot read the token (same-origin policy) so it cannot include it.

CSRF protection is checked for methods that change state: POST, PUT, PATCH, DELETE. GET, HEAD, OPTIONS and TRACE are ignored, which is why GET requests must never change data.

When do you need CSRF protection?

SituationCSRF needed?Reason
Browser app, session cookie authenticationYESBrowsers send cookies automatically
SPA with session cookieYESSame reason. Configure the cookie based token
API using an Authorization: Bearer header with JWT stored in memory or localStorageNoThe browser does not add the header automatically, so evil.com cannot send it
API using JWT stored in a cookieYESThe cookie is sent automatically again
HTTP Basic with browser credential cachingYESBrowser sends the cached credentials automatically

Thymeleaf and forms

<!-- Thymeleaf adds the hidden _csrf field automatically for th:action forms -->
<form th:action="@{/transfer}" method="post">
    <input name="to"><input name="amount"><button>Send</button>
</form>
<!-- Plain HTML: add it yourself -->
<input type="hidden" th:name="${_csrf.parameterName}" th:value="${_csrf.token}"/>

SPA with cookie based token (Angular and React style)

http.csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())       // cookie XSRF-TOKEN readable by JavaScript
        .csrfTokenRequestHandler(new SpaCsrfTokenRequestHandler()));

// Spring Security 6 masks the token (BREACH protection). SPAs need a handler that accepts the raw cookie value in the header:
final class SpaCsrfTokenRequestHandler implements CsrfTokenRequestHandler {
    private final CsrfTokenRequestHandler plain = new CsrfTokenRequestAttributeHandler();
    private final CsrfTokenRequestHandler xor = new XorCsrfTokenRequestAttributeHandler();

    @Override
    public void handle(HttpServletRequest request, HttpServletResponse response, Supplier<CsrfToken> csrfToken) {
        this.xor.handle(request, response, csrfToken);         // makes the token available (masked) for rendering
        csrfToken.get();                                        // forces the deferred token to be loaded so the cookie is written
    }

    @Override
    public String resolveCsrfTokenValue(HttpServletRequest request, CsrfToken csrfToken) {
        String headerValue = request.getHeader(csrfToken.getHeaderName());
        return (StringUtils.hasText(headerValue) ? this.plain : this.xor).resolveCsrfTokenValue(request, csrfToken);
    }
}
// Angular reads cookie XSRF-TOKEN and sends header X-XSRF-TOKEN automatically. In fetch/axios, copy the cookie value into the header yourself.

Disable it only for stateless token APIs

http.csrf(csrf -> csrf.disable())
    .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
// or exclude only some paths:  csrf.ignoringRequestMatchers("/api/webhooks/**")  (webhooks are verified by a signature)

Extra layer: SameSite cookies

SameSite=Lax (default in modern browsers) stops the browser from sending the cookie on cross-site POST requests. SameSite=Strict blocks it for all cross-site navigation. This is a strong second line of defense, but do not remove the CSRF token because of it (old browsers, subdomain attacks).

Common mistake: Turning CSRF off in a session based application because a POST returned 403. The 403 means the token is missing. Send the token (form field or header) instead of removing the protection.

Interview questions

Why is GET exempt from CSRF checks?

GET must be safe (no state change). CSRF protection is only about state changes, so GET, HEAD and OPTIONS are not checked. If GET changes data, you have a design bug.

Do JWT APIs need CSRF?

Not when the token is sent in the Authorization header by your JavaScript. They do when the JWT is stored in a cookie, because the browser sends cookies automatically.

Why does a POST from Postman return 403?

CSRF protection is on and the request has no token. For a stateless API disable CSRF and use token authentication, or send the token in the header.
