CORS and Security Headers

CORS is a browser rule that decides which websites may call your API from JavaScript. Security headers tell the browser how to treat your pages. Both are often misconfigured, and both cause the most confusing browser errors.

Same-origin policy and CORS

An origin is scheme + host + port (https://app.example.com:443). By default a page can only call APIs of its own origin. CORS (Cross-Origin Resource Sharing) lets your API say: I allow these other origins. CORS is enforced by the browser, not by the server: curl and Postman ignore it. It is not authentication.

Browser page at https://app.example.com calls https://api.example.com/orders  (different origin)

SIMPLE request (GET, no custom headers):    browser sends it with   Origin: https://app.example.com
                                             server answers with     Access-Control-Allow-Origin: https://app.example.com
                                             browser lets JavaScript read the response

PREFLIGHT (PUT/DELETE, JSON, Authorization header ...):
   1. browser sends OPTIONS /orders   Origin: ... ; Access-Control-Request-Method: PUT ; Access-Control-Request-Headers: authorization
   2. server answers 200  Access-Control-Allow-Origin, -Allow-Methods, -Allow-Headers, -Max-Age
   3. only then the browser sends the real PUT request
If the preflight is answered with 401 (security blocked it), the browser reports a CORS error.

Configure CORS correctly with Spring Security

@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http.cors(Customizer.withDefaults())                            // uses the CorsConfigurationSource bean, runs BEFORE authorization
        .authorizeHttpRequests(a -> a.anyRequest().authenticated());
    return http.build();
}

@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration cfg = new CorsConfiguration();
    cfg.setAllowedOrigins(List.of("https://app.example.com"));      // exact origins. Not "*" when credentials are allowed
    cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
    cfg.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-Requested-With"));
    cfg.setExposedHeaders(List.of("Location", "X-Request-Id"));     // headers JavaScript may read
    cfg.setAllowCredentials(true);                                  // cookies and Authorization allowed
    cfg.setMaxAge(Duration.ofHours(1));                             // cache the preflight
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", cfg);
    return source;
}
MistakeResult
allowedOrigins('*') with allowCredentials(true)Rejected by Spring and by browsers. Use exact origins or allowedOriginPatterns
Reflecting any Origin header backAny website can call your API with the user's cookies
CORS configured only in @CrossOrigin or WebMvcConfigurer but Security not told to use itPreflight is rejected with 401 before Spring MVC sees it
Thinking CORS protects the APIIt does not. Attackers use curl. Always use authentication and authorization

Security headers

http.headers(h -> h
    .contentSecurityPolicy(csp -> csp.policyDirectives(
        "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; "
      + "frame-ancestors 'none'; base-uri 'self'; form-action 'self'"))
    .httpStrictTransportSecurity(hsts -> hsts.includeSubDomains(true).maxAgeInSeconds(31536000).preload(true))
    .frameOptions(frame -> frame.deny())
    .contentTypeOptions(Customizer.withDefaults())                                   // X-Content-Type-Options: nosniff
    .referrerPolicy(r -> r.policy(ReferrerPolicyHeaderWriter.ReferrerPolicy.STRICT_ORIGIN_WHEN_CROSS_ORIGIN))
    .permissionsPolicyHeader(p -> p.policy("camera=(), microphone=(), geolocation=()")));
HeaderPurpose
Content-Security-PolicyWhitelist where scripts, styles, images and frames may load from. The best defense against XSS impact
Strict-Transport-SecurityBrowser must use HTTPS for this domain for a year
X-Frame-Options / frame-ancestorsStops clickjacking (your page inside another site's frame)
X-Content-Type-Options: nosniffBrowser must trust the declared content type
Referrer-PolicyLimits URL information sent to other sites
Permissions-PolicyTurn off browser features (camera, microphone, location)
Cache-Control: no-storeFor responses with private data (Spring Security sets this by default)
  • Pure REST APIs return JSON, so CSP matters less there. It matters a lot for HTML pages and SPAs.
  • Start with Content-Security-Policy-Report-Only to find what would break, then enforce.
  • Test your headers with securityheaders.com or the browser developer tools.

Common mistake: Fixing a CORS error by allowing all origins with credentials. This lets any website use the logged-in user's browser against your API. List the exact origins you trust.

Interview questions

Why does the browser show a CORS error while Postman works?

CORS is a browser enforced rule. Postman does not enforce it. The browser blocks JavaScript from reading responses without the right Access-Control headers.

What is a preflight request?

An automatic OPTIONS request the browser sends before certain cross-origin calls to ask the server whether the real request is allowed.

Does CORS protect my API from attackers?

No. It only limits what browsers allow web pages to do. Anybody can call your API with other tools, so always authenticate and authorize.
