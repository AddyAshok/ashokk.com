Common Attacks and Defenses in Spring Applications

A practical guide to the attacks you must defend against (OWASP Top 10 style) with the Spring specific defense for each. Use it as a design review checklist.

Attack and defense map

AttackHow it worksDefense in a Spring app
SQL injectionUser input becomes part of the SQL textUse Spring Data, JPA parameters, JdbcTemplate placeholders. Never concatenate strings into SQL/JPQL
XSSScript injected into a page runs in the victim's browserOutput encoding (Thymeleaf escapes by default), CSP header, HttpOnly cookies, validate input, sanitize rich text
CSRFCross-site request with the victim's cookieCSRF tokens, SameSite cookies
Broken access control / IDORChange an id in the URL to see others' dataAuthorize per object (owner check), method security
Mass assignment (over-posting)Client sends extra JSON fields such as role=ADMIN that bind to an entityBind to request DTOs with only allowed fields, never to entities
Brute force / credential stuffingAutomated password guessingSlow hashing, lockout, rate limiting, CAPTCHA, MFA
Session fixation / hijackingSteal or set the session idChange id at login, HttpOnly Secure cookies, HTTPS
SSRFThe server is tricked to call internal URLsAllow-list target hosts, block private IP ranges, no redirects, timeouts
Path traversal../ in file namesNormalize paths, generate own file names, check startsWith(root)
Insecure deserializationMalicious serialized objectsDo not use Java serialization on untrusted data. JSON with typed DTOs. No default typing in Jackson
Sensitive data exposureSecrets in logs, error pages, GitDo not log secrets, hide stack traces, environment variables or a vault, encrypt at rest
Vulnerable dependenciesKnown CVEs in librariesRegular updates, dependency scanning (OWASP Dependency-Check, Dependabot), Boot BOM updates
Security misconfigurationOpen actuator, swagger, H2 console, default passwordsExpose only needed endpoints, profiles per environment, deny by default

SQL injection: the wrong and the right way

// WRONG: string concatenation
String jpql = "select u from AppUser u where u.email = '" + email + "'";       // email = ' or '1'='1  returns all users
em.createQuery(jpql, AppUser.class).getResultList();

// RIGHT: parameters
em.createQuery("select u from AppUser u where u.email = :email", AppUser.class).setParameter("email", email).getResultList();
jdbc.query("select * from users where email = ?", mapper, email);
repository.findByEmail(email);                                               // derived query is always parameterized

// Dynamic ORDER BY needs an allow-list, because column names cannot be parameters
Set<String> allowed = Set.of("name", "price");
if (!allowed.contains(sort)) throw new IllegalArgumentException("Invalid sort field");

Mass assignment

// WRONG: binding the request straight to the entity. A client can send {"email":"x","role":"ADMIN","enabled":true}
@PostMapping("/register") public AppUser register(@RequestBody AppUser user) { return repo.save(user); }

// RIGHT: a DTO with only the fields the client may set
public record RegisterRequest(@Email String email, @Size(min = 12) String password) { }
@PostMapping("/register") public void register(@Valid @RequestBody RegisterRequest req) { service.register(req.email(), req.password()); }

XSS

  • Thymeleaf th:text escapes HTML. th:utext does NOT. Never use th:utext with user data.
  • Never build HTML strings from user data in Java. If users may submit HTML, sanitize it with a library such as OWASP Java HTML Sanitizer.
  • Send JSON APIs with Content-Type application/json and X-Content-Type-Options: nosniff.
  • Add a Content-Security-Policy that forbids inline scripts. This limits damage if an injection happens.

Rate limiting the login and sensitive endpoints

@Component
public class RateLimitFilter extends OncePerRequestFilter {

    private final StringRedisTemplate redis;
    public RateLimitFilter(StringRedisTemplate redis) { this.redis = redis; }

    @Override
    protected boolean shouldNotFilter(HttpServletRequest req) { return !req.getRequestURI().startsWith("/auth/"); }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String key = "rl:" + req.getRemoteAddr() + ":" + (System.currentTimeMillis() / 60_000);      // per IP, per minute
        Long count = redis.opsForValue().increment(key);
        if (count != null && count == 1) redis.expire(key, Duration.ofMinutes(2));
        if (count != null && count > 20) {
            res.setStatus(429);
            res.setHeader("Retry-After", "60");
            res.getWriter().write("{\"error\":\"Too many requests\"}");
            return;
        }
        chain.doFilter(req, res);
    }
}
// Behind a proxy use server.forward-headers-strategy=framework so getRemoteAddr is the client IP. Better: rate limit at the gateway.

SSRF guard for URL fetching features

public static void assertSafe(String url) throws UnknownHostException {
    URI uri = URI.create(url);
    if (!"https".equalsIgnoreCase(uri.getScheme())) throw new IllegalArgumentException("Only https");
    for (InetAddress a : InetAddress.getAllByName(uri.getHost())) {
        if (a.isAnyLocalAddress() || a.isLoopbackAddress() || a.isLinkLocalAddress() || a.isSiteLocalAddress())
            throw new IllegalArgumentException("Internal address not allowed");          // blocks 127.x, 10.x, 192.168.x, 169.254.x (cloud metadata)
    }
}

Configuration hygiene

  • Restrict Actuator: expose only health and info publicly, secure the rest, use another port.
  • Disable Swagger UI, H2 console and debug features in production.
  • server.error.include-stacktrace=never, server.error.include-message=never.
  • Use separate secrets per environment. Rotate leaked secrets at once.
  • Log security events (login failures, access denied, password changes) without logging secrets.

Common mistake: Believing that using Spring Security means the application is secure. The framework cannot know your business rules: IDOR, mass assignment, injection and misconfiguration are your responsibility. Review each endpoint with the table above.

Interview questions

Is JPA safe from SQL injection?

Parameterized queries and derived queries are. Building JPQL or native SQL with string concatenation is not.

What is the most common API vulnerability?

Broken object level authorization: checking login but not whether the user may access that specific record.

How do I prevent mass assignment?

Never bind requests to entities. Use request DTOs that list only the fields a client may send.
