Application Security and Spring Security Overview

Spring Security is the standard security framework for Spring applications. It gives you authentication (who are you), authorization (what may you do) and protection against common attacks. Before the code, you need the mental model: what threats exist, what a security framework must do, and how Spring Security solves it with servlet filters.

The two big questions

TermQuestionExampleFails with
Authentication (authn)Who are you?Login with username and password, or a valid token401 Unauthorized
Authorization (authz)What are you allowed to do?Only ADMIN can delete a user403 Forbidden

What can go wrong: threat map

ThreatMeaningSpring Security defense
Broken authenticationWeak passwords, stolen sessions or tokensPassword encoders, session protection, token validation
Broken access controlUser A reads user B's dataAuthorization rules, method security
CSRFAnother site makes your browser send a request with your cookieCSRF tokens (on by default)
Session fixationAttacker sets the victim's session id before loginNew session id after login (on by default)
ClickjackingYour page is hidden inside a frameX-Frame-Options / CSP frame-ancestors (on by default)
XSSInjected script steals tokens or sessionsSecurity headers (CSP), output encoding, HttpOnly cookies
Brute forceTrying many passwordsSlow password hashing, lockout and rate limiting (you add)
Man in the middleTraffic is read on the networkHTTPS, HSTS header

How Spring Security fits into your application

HTTP request
   ▼
Servlet container (Tomcat) ─► servlet Filter chain
   ▼
DelegatingFilterProxy  ("springSecurityFilterChain")          ← the ONE servlet filter Spring Security registers
   ▼
FilterChainProxy                                               ← a Spring bean; chooses the right SecurityFilterChain
   ▼
SecurityFilterChain  = ordered list of security filters (about 15)
   ├─ read credentials / token          (authentication filters)
   ├─ build the Authentication object   (AuthenticationManager)
   ├─ store it in SecurityContextHolder (ThreadLocal)
   ├─ protect against attacks           (CSRF, headers, CORS)
   └─ check access rules                (AuthorizationFilter)
   ▼
DispatcherServlet ─► your controller     (security is finished BEFORE your code runs)
  • Spring Security is filter based. It works before Spring MVC, so it protects every servlet path, even static files.
  • It is configured with SecurityFilterChain beans (lambda DSL) in Spring Security 6 and 7. The old WebSecurityConfigurerAdapter is gone.
  • It has three big areas: Authentication, Authorization and Protection against exploits.
  • Method security (@PreAuthorize) is separate: it uses AOP proxies inside your service layer.

Minimum setup

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-test</artifactId>
    <scope>test</scope>
</dependency>

The moment this dependency is on the classpath, the whole application is secured. The next page explains exactly what that default security does, line by line.

Common mistake: Thinking security is a feature you add at the end. Design who can do what (roles, ownership rules) with the API itself, and write tests for 401 and 403 from the first endpoint.

Interview questions

Authentication or authorization, which comes first?

Authentication first. The system must know who you are before it can decide what you are allowed to do.

Is Spring Security only for web login?

No. It also secures REST APIs, method calls, WebSockets, messaging, and supports OAuth2, OIDC, SAML, LDAP and JWT.

Why is security done in filters and not in controllers?

Filters run before the request reaches Spring MVC, so unauthorized requests never touch business code, and the same rules protect every endpoint.
