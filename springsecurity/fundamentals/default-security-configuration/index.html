Default Spring Security Configuration: What Happens When You Add the Starter

Add spring-boot-starter-security and do nothing else: every URL asks for a login. This page explains exactly which classes create this behavior, what the default filter chain contains, what the generated password is, which headers and protections are on, and what the default does NOT protect. Knowing the default well is the base for every customization.

What you see

Using generated security password: 8e557245-73e2-4286-969a-ff57fe326336

This generated password is for development use only. Your security configuration must be updated before running your application in production.
  • Every URL, including /, static files and /actuator, redirects a browser to a generated login page at /login.
  • User name is user. The password is a random UUID printed at every startup.
  • API clients (curl) get 401 with the header WWW-Authenticate: Basic realm="Realm".
curl -i http://localhost:8080/api/hello
# HTTP/1.1 401     WWW-Authenticate: Basic realm="Realm"
curl -u user:8e557245-73e2-4286-969a-ff57fe326336 http://localhost:8080/api/hello    # 200
curl -i -H "Accept: text/html" http://localhost:8080/api/hello
# HTTP/1.1 302  Location: http://localhost:8080/login    (browser style: redirect to the login page)

Which classes create the default behavior?

spring-boot-autoconfigure (AutoConfiguration.imports)
 ├─ SecurityAutoConfiguration
 │     └─ imports SpringBootWebSecurityConfiguration        (only for servlet web apps)
 │           └─ @Bean SecurityFilterChain defaultSecurityFilterChain(HttpSecurity http)
 │                 @ConditionalOnDefaultWebSecurity        ← only when YOU did NOT define a SecurityFilterChain bean
 │                     http.authorizeHttpRequests(r -> r.anyRequest().authenticated());
 │                     http.formLogin(withDefaults());
 │                     http.httpBasic(withDefaults());
 │
 ├─ UserDetailsServiceAutoConfiguration
 │     └─ @Bean InMemoryUserDetailsManager                 (one user from spring.security.user.*)
 │           @ConditionalOnMissingBean(AuthenticationManager, AuthenticationProvider, UserDetailsService, JwtDecoder ...)
 │           password = "{noop}" + generated UUID, roles = none
 │
 ├─ SecurityFilterAutoConfiguration
 │     └─ registers DelegatingFilterProxy "springSecurityFilterChain" in the servlet container
 │           order = spring.security.filter.order (default -100: before almost every other filter)
 │
 └─ WebSecurityEnablerConfiguration  ─► @EnableWebSecurity (turns on the Spring Security machinery)

The rule behind every 'default': @ConditionalOnMissingBean. As soon as you define your own SecurityFilterChain bean, the default chain disappears completely (it does not merge). As soon as you define your own UserDetailsService, the generated user disappears.

The default configuration written out as code

@Configuration
@EnableWebSecurity
public class EquivalentOfTheDefault {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())   // everything needs login
            .formLogin(Customizer.withDefaults())                               // generated HTML login page
            .httpBasic(Customizer.withDefaults());                              // Authorization: Basic ...
        return http.build();
    }
}
// plus (also defaults): csrf(), headers(), sessionManagement(), logout(), anonymous(), requestCache(),
//                       securityContext(), servletApi(), exceptionHandling()

Default filter chain, in order

#FilterWhat it does by default
1DisableEncodeUrlFilterStops the session id from being added to URLs (;jsessionid=)
2WebAsyncManagerIntegrationFilterPasses the SecurityContext to async request threads
3SecurityContextHolderFilterLoads the SecurityContext (from the HTTP session) into SecurityContextHolder, clears it at the end
4HeaderWriterFilterAdds the security response headers (see below)
5CsrfFilterRequires a valid CSRF token for POST, PUT, PATCH and DELETE
6LogoutFilterHandles POST /logout: invalidate session, clear context
7UsernamePasswordAuthenticationFilterHandles POST /login (fields username and password)
8DefaultLoginPageGeneratingFilterGenerates the HTML login page for GET /login
9DefaultLogoutPageGeneratingFilterGenerates the logout confirmation page for GET /logout
10BasicAuthenticationFilterReads the Authorization: Basic header
11RequestCacheAwareFilterAfter login, replays the request that was saved before the redirect to /login
12SecurityContextHolderAwareRequestFilterMakes request.getUserPrincipal(), isUserInRole() work
13AnonymousAuthenticationFilterIf nobody is authenticated, puts an anonymous user (anonymousUser, ROLE_ANONYMOUS) into the context
14SessionManagementFilterSession fixation and concurrency handling after authentication
15ExceptionTranslationFilterTurns AuthenticationException into login redirect or 401, AccessDeniedException into 403
16AuthorizationFilterThe final check: anyRequest().authenticated()

See the real chain of your own application with logging.level.org.springframework.security=TRACE (it prints 'Will secure any request with [...]' at startup), or with @EnableWebSecurity(debug = true) during development only.

What happens on the first request (browser)

1. GET /orders  (no session)
     ... SecurityContextHolderFilter: no context ... AnonymousAuthenticationFilter: anonymousUser
     AuthorizationFilter: anyRequest().authenticated()  ─► anonymous is not authenticated ─► AccessDeniedException
     ExceptionTranslationFilter:
         ├─ saves the request /orders in the HttpSession (RequestCache)
         └─ starts authentication: entry point = redirect to /login          [302]
2. GET /login  ─► DefaultLoginPageGeneratingFilter renders the HTML form (with a hidden _csrf field)
3. POST /login  username=user&password=...&_csrf=...
     CsrfFilter validates the token
     UsernamePasswordAuthenticationFilter ─► AuthenticationManager ─► DaoAuthenticationProvider
         ─► InMemoryUserDetailsManager.loadUserByUsername("user") ─► DelegatingPasswordEncoder.matches
     success:  session id is CHANGED (fixation protection), SecurityContext saved in the session,
               redirect to the SAVED request /orders   [302]
4. GET /orders (JSESSIONID cookie) ─► context loaded from the session ─► authenticated ─► controller runs

Default entry point for APIs vs browsers

Because formLogin and httpBasic are both on, Spring Security uses a DelegatingAuthenticationEntryPoint that picks by request: requests with X-Requested-With: XMLHttpRequest get 401 with a Basic challenge, requests that accept text/html are redirected to /login, and all other clients (curl, Postman, mobile apps) get 401 with WWW-Authenticate: Basic.

Default response headers

HeaderValueProtects against
Cache-Controlno-cache, no-store, max-age=0, must-revalidate (plus Pragma and Expires)Sensitive pages cached in the browser
X-Content-Type-OptionsnosniffMIME sniffing attacks
X-Frame-OptionsDENYClickjacking
Strict-Transport-Securitymax-age=31536000 ; includeSubDomains (only on HTTPS responses)Downgrade to HTTP
X-XSS-Protection0 (disabled on purpose: the old browser filter caused problems)Use CSP instead

Not added by default: Content-Security-Policy, Referrer-Policy, Permissions-Policy. Add them yourself (see the headers page).

Other defaults you should know

AreaDefault behavior
CSRFEnabled. Token stored in the HttpSession (HttpSessionCsrfTokenRepository). Token is BREACH protected by XOR masking. GET, HEAD, OPTIONS, TRACE are exempt

Login failureRedirect to /login?error
Remember meOff
CORSNot configured. Browser cross-origin calls are blocked by the browser policy
ActuatorBoot secures /actuator/** with the same default chain (only health is exposed over HTTP by default)

Method securityOff. @PreAuthorize does nothing until you add @EnableMethodSecurity

Change the default user (development only)

spring.security.user.name=admin
spring.security.user.password=changeit
spring.security.user.roles=ADMIN,USER

What the default does NOT give you

  • No real users: one in-memory user, recreated at every start.
  • No role based rules: all authenticated users can do everything.
  • No protection against brute force: unlimited login attempts.
  • No CSP header, no rate limiting, no account lockout, no audit log.
  • No token support (JWT): browsers use sessions, APIs use Basic auth (password on every request).
  • Everything needs login, including the health endpoint used by load balancers and static files.

First customization: the smallest useful SecurityFilterChain

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/css/**", "/js/**", "/actuator/health").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .formLogin(Customizer.withDefaults())
            .logout(Customizer.withDefaults());
        return http.build();
    }

    @Bean
    UserDetailsService users(PasswordEncoder encoder) {
        return new InMemoryUserDetailsManager(
            User.withUsername("ram").password(encoder.encode("ram123")).roles("USER").build(),
            User.withUsername("admin").password(encoder.encode("admin123")).roles("ADMIN", "USER").build());
    }

    @Bean
    PasswordEncoder passwordEncoder() { return PasswordEncoderFactories.createDelegatingPasswordEncoder(); }
}

Common mistake: Leaving the generated password and default chain in production, or copying an example that disables everything (csrf disable and permitAll on any request) because it 'made the error go away'. Understand why a request is rejected (TRACE logging) and open only what is needed.

Interview questions

Why does everything ask for a password after adding the starter?

Boot creates a default SecurityFilterChain with anyRequest().authenticated(), formLogin and httpBasic, because no other SecurityFilterChain bean exists.

How do I turn off the default configuration?

Define your own SecurityFilterChain bean. The default one has @ConditionalOnDefaultWebSecurity and backs off. Do not exclude SecurityAutoConfiguration unless you know why.

Where does the generated password come from?

UserDetailsServiceAutoConfiguration creates an InMemoryUserDetailsManager with a random UUID password (prefixed with {noop}) when you define no UserDetailsService, AuthenticationManager or AuthenticationProvider.
