The Security Filter Chain in Depth: Order, Customization and Multiple Chains

The filter order is fixed by Spring Security. Knowing where each filter sits tells you where to add custom filters, and why a request is rejected before or after some step. This page also covers multiple chains, matchers and debugging.

Filters and their fixed order

(position)  filter                                  role
   1    DisableEncodeUrlFilter                    no session id in URLs
   2    WebAsyncManagerIntegrationFilter          context for async threads
   3    SecurityContextHolderFilter               load/clear the SecurityContext
   4    HeaderWriterFilter                        security headers
   5    CorsFilter                                CORS (only when http.cors() is enabled)
   6    CsrfFilter                                CSRF token check
   7    LogoutFilter                              /logout
   8    OAuth2AuthorizationRequestRedirectFilter  (oauth2Login only)
   9    UsernamePasswordAuthenticationFilter      form login   ◄── common place for a custom "before"
  10    DefaultLoginPageGeneratingFilter          /login page
  11    BasicAuthenticationFilter                 HTTP Basic
  12    BearerTokenAuthenticationFilter           JWT / opaque token (oauth2ResourceServer only)
  13    RequestCacheAwareFilter                   replay saved request
  14    SecurityContextHolderAwareRequestFilter   servlet API methods
  15    AnonymousAuthenticationFilter             anonymous user
  16    SessionManagementFilter                   session fixation, concurrency
  17    ExceptionTranslationFilter                401 / 403 handling
  18    AuthorizationFilter                       access rules   ◄── LAST

Not all filters exist in every chain: the chain contains only those for the features you enabled. ExceptionTranslationFilter wraps only the filters AFTER it, which is why AuthorizationFilter (after it) can throw AccessDeniedException and get a clean 403, but exceptions thrown by a filter placed BEFORE it are not translated.

Adding a custom filter

http.addFilterBefore(myFilter, UsernamePasswordAuthenticationFilter.class);   // run before that filter
http.addFilterAfter(myFilter, BasicAuthenticationFilter.class);              // run after
http.addFilterAt(myFilter, UsernamePasswordAuthenticationFilter.class);      // same position (order between them undefined)

// Typical: put a token filter before UsernamePasswordAuthenticationFilter, an audit/log filter after AuthorizationFilter
// A filter that logs who is calling (runs after authentication is done)
public class AuditFilter extends OncePerRequestFilter {
    private static final Logger log = LoggerFactory.getLogger(AuditFilter.class);

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        chain.doFilter(req, res);
        Authentication a = SecurityContextHolder.getContext().getAuthentication();
        log.info("{} {} user={} status={}", req.getMethod(), req.getRequestURI(),
                 a == null ? "-" : a.getName(), res.getStatus());
    }
}
// http.addFilterAfter(new AuditFilter(), AuthorizationFilter.class);

Tip: Do not annotate a security filter with @Component. Spring Boot would also register it as a normal servlet filter, and it would run twice (once outside and once inside the chain). Create it with new inside the SecurityFilterChain bean, or register a FilterRegistrationBean with setEnabled(false).

Request matchers and rule order

http.authorizeHttpRequests(auth -> auth
    .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()          // method + path
    .requestMatchers("/api/admin/**").hasRole("ADMIN")
    .requestMatchers("/api/orders/**").hasAnyRole("USER", "ADMIN")
    .requestMatchers(new AntPathRequestMatcher("/legacy/*.jsp")).denyAll()    // explicit matcher type
    .requestMatchers(RegexRequestMatcher.regexMatcher("/files/[0-9]+")).authenticated()
    .anyRequest().denyAll());                                                 // safest default: deny by default
  • Rules are checked from top to bottom. The FIRST match decides. Put the most specific rules first.
  • Finish with anyRequest().denyAll() or authenticated(). A forgotten endpoint should be closed, not open.
  • With Spring MVC, requestMatchers(String) uses MvcRequestMatcher rules (the same as your controllers). Servlet paths and trailing slash differences are a common source of bypasses. Test with real requests.
  • authorizeHttpRequests replaces the old authorizeRequests: it uses AuthorizationManager and is checked for every dispatch type.

Multiple SecurityFilterChains

@Bean @Order(1)
SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**")                       // this chain handles only /api/**
        .csrf(csrf -> csrf.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .authorizeHttpRequests(a -> a.anyRequest().authenticated());
    return http.build();
}

@Bean @Order(2)
SecurityFilterChain webChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.requestMatchers("/login", "/css/**").permitAll().anyRequest().authenticated())
        .formLogin(Customizer.withDefaults());
    return http.build();                                  // no securityMatcher = matches everything (must be last)
}

FilterChainProxy uses the FIRST chain whose securityMatcher matches, and only that chain is used. A chain without securityMatcher matches every request, so it must have the lowest priority.

Debugging checklist

logging.level.org.springframework.security=TRACE
# TRACE prints: the list of filters at startup, which chain matched, each filter, the authorization decision and why access was denied
SymptomLikely reason
401 for a public endpointRule order wrong, or the URL does not match (context path, trailing slash), or the endpoint is under a different chain
403 on POST onlyCSRF token missing
403 for a logged-in userRole name mismatch: hasRole('ADMIN') needs the authority ROLE_ADMIN
Redirect to /login for an API callformLogin is enabled. Use httpBasic or a token and an entry point returning 401
Custom filter runs twiceIt is also a @Component (servlet filter registration)
CORS preflight gets 401http.cors() is missing, so OPTIONS reaches authorization
Static files blockedrequestMatchers for /css/** etc. missing, or PathRequest.toStaticResources() not permitted

Common mistake: Placing a broad permitAll rule before specific rules (for example /** first). The first match wins, so the later, stricter rules are never reached and your API is open.

Interview questions

What decides which SecurityFilterChain handles a request?

FilterChainProxy checks the chains in order (by @Order) and uses the first whose securityMatcher matches the request.

Where should a JWT filter be added?

Before UsernamePasswordAuthenticationFilter, so the SecurityContext is filled before the authorization check. With oauth2ResourceServer this is already done by BearerTokenAuthenticationFilter.

Why is anyRequest() required to be last?

Because it matches every request. Spring Security throws an error at startup if you add rules after anyRequest().
