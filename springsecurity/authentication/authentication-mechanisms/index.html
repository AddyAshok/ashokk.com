Authentication Mechanisms Compared

Spring Security supports many ways to prove identity. Choose the mechanism that fits your client type and threat model. This page compares them and shows the minimal configuration of each.

Form login with custom page and handlers

http.formLogin(form -> form
        .loginPage("/login")                              // your own page (permit it!)
        .loginProcessingUrl("/perform_login")             // where the form posts
        .usernameParameter("email")
        .defaultSuccessUrl("/dashboard", false)           // false = go back to the saved request if there is one
        .failureUrl("/login?error")
        .permitAll())
    .logout(logout -> logout
        .logoutUrl("/logout")
        .logoutSuccessUrl("/login?logout")
        .deleteCookies("JSESSIONID")
        .invalidateHttpSession(true));

HTTP Basic for APIs

http.httpBasic(basic -> basic.realmName("Shop API"))
    .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .csrf(csrf -> csrf.disable());
// header: Authorization: Basic base64(username:password)
// Use it only over HTTPS, and preferably not for end users.

API key filter

public class ApiKeyFilter extends OncePerRequestFilter {
    private final ApiKeyService keys;
    public ApiKeyFilter(ApiKeyService keys) { this.keys = keys; }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String key = req.getHeader("X-API-Key");
        if (key != null) {
            keys.findClient(key).ifPresent(client -> SecurityContextHolder.getContext().setAuthentication(
                    UsernamePasswordAuthenticationToken.authenticated(client.name(), null,
                            List.of(new SimpleGrantedAuthority("ROLE_PARTNER")))));
        }
        chain.doFilter(req, res);
    }
}
// Store only a HASH of each key, give keys an expiry and a scope, and allow rotation.

Remember-me: persistent token approach

http.rememberMe(r -> r
        .tokenRepository(new JdbcTokenRepositoryImpl() {{ setDataSource(dataSource); }})   // table persistent_logins
        .tokenValiditySeconds(14 * 24 * 3600)
        .key(rememberMeKey));                                                               // secret from the environment

The simple hash-based variant puts username, expiry and a hash of the password in the cookie, which is weak. The persistent token variant stores random series and token values in a table and changes the token at every use, so theft can be detected.

How to choose

  • Browser app rendered by the server: form login + session (with CSRF).
  • Single page app with your own backend: session cookie (HttpOnly, SameSite) is often simpler and safer than JWT in localStorage.
  • Mobile app or many microservices: OAuth2 with short-lived JWT access tokens and refresh tokens.
  • Machine to machine: OAuth2 client credentials or mTLS. API keys only for simple cases.
  • Enterprise users: OIDC or SAML with the company identity provider.

Common mistake: Choosing JWT for every project only because it is popular. A server-rendered application or a simple SPA with the same backend is usually safer and simpler with a normal HttpOnly session cookie.

Interview questions

Is HTTP Basic secure?

Only over HTTPS. The password is sent with every request and there is no logout, so it suits internal tools and service-to-service calls, not end users.

Session or JWT for a REST API?

Sessions are simple and revocable but need shared session storage when you scale. JWT is stateless and good across services, but hard to revoke. Decide by scaling needs, client type and revocation requirements.

Why is remember-me risky?

The cookie is a long-lived credential. If it is stolen, the attacker stays logged in. Use the persistent token version, HTTPS and require re-authentication for sensitive actions.
