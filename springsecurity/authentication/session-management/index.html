Session Management: Fixation, Concurrency, Timeouts and Spring Session

For session based applications, the session id is the credential. Protect it, limit it, and store it correctly when you run several instances.

How a session login works

POST /login (correct password)
   ─► SecurityContext created ─► session id CHANGED (fixation protection) ─► context saved into HttpSession
   ─► Set-Cookie: JSESSIONID=ABC...; Path=/; HttpOnly; Secure; SameSite
Next request: Cookie: JSESSIONID=ABC ─► SecurityContextHolderFilter loads context from the session
The session id is now equal to the password for as long as the session lives: stealing it means being logged in.

Session fixation protection

Attack: the attacker gets a valid session id from your site (unauthenticated), tricks the victim into using it (link or cookie injection), and waits for the victim to log in. If the id stays the same after login, the attacker's copy becomes authenticated. Spring Security prevents this by changing the session id at login.

http.sessionManagement(s -> s
    .sessionFixation(f -> f.changeSessionId())      // default: keep attributes, new id (also newSession, migrateSession, none)
    .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
    .maximumSessions(1)                             // only one active login per user
        .maxSessionsPreventsLogin(false)            // false: new login kicks the old session out. true: block the new login
        .expiredUrl("/login?expired")
    .and()
    .invalidSessionUrl("/login?invalid"));
Creation policyMeaningUse
ALWAYSAlways create a sessionRare
IF_REQUIRED (default)Create when neededWeb apps
NEVERDo not create, but use an existing oneRare
STATELESSNever create or use a session. Every request must authenticate itselfToken based APIs

Concurrent sessions

@Bean
HttpSessionEventPublisher httpSessionEventPublisher() { return new HttpSessionEventPublisher(); }   // needed so the registry sees session ends

@Autowired SessionRegistry sessionRegistry;     // define: @Bean SessionRegistry sessionRegistry() { return new SessionRegistryImpl(); }

public List<String> loggedInUsers() {
    return sessionRegistry.getAllPrincipals().stream()
        .filter(p -> !sessionRegistry.getAllSessions(p, false).isEmpty())
        .map(p -> ((UserDetails) p).getUsername()).toList();
}
// force logout of a user:  sessionRegistry.getAllSessions(principal, false).forEach(SessionInformation::expireNow);

Cookie and timeout settings

server.servlet.session.timeout=30m
server.servlet.session.cookie.http-only=true       # JavaScript cannot read the cookie (limits XSS damage)
server.servlet.session.cookie.secure=true          # sent only over HTTPS
server.servlet.session.cookie.same-site=lax        # limits CSRF (strict is safer, may break login from external links)
server.servlet.session.cookie.name=SESSION
server.servlet.session.tracking-modes=cookie       # no session id in URLs

Several instances: Spring Session with Redis

With a normal HttpSession each server keeps sessions in its own memory. Behind a load balancer the user can land on another server and appear logged out. Options: sticky sessions (fragile), or store sessions in Redis or a database with Spring Session, so all instances share them.

<dependency><groupId>org.springframework.session</groupId><artifactId>spring-session-data-redis</artifactId></dependency>
<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-data-redis</artifactId></dependency>
spring.session.store-type=redis
spring.session.timeout=30m
spring.session.redis.namespace=shop:sessions
  • Session data must be serializable. Keep it small (only the security context and few attributes).
  • Redis gives a real logout everywhere and central control (delete a session = user logged out).
  • Compare: JWT needs no session storage but cannot be revoked without a deny list, which is also shared state.

Logout done right

  • Invalidate the HTTP session and clear the SecurityContext (LogoutFilter does this).
  • Delete the cookie, and use POST with a CSRF token for logout.
  • For tokens: revoke the refresh token on the server. The access token stays valid until it expires, so keep it short.

Common mistake: Keeping sessions forever and putting the session id in the URL. Set a reasonable timeout, HttpOnly, Secure and SameSite cookies, and never allow URL-based session tracking.

Interview questions

What is session fixation?

An attack where the attacker forces the victim to use a session id the attacker knows, then waits for the victim to log in. The fix is to change the session id after login, which Spring Security does by default.

Why do I lose my session behind a load balancer?

Sessions live in the memory of one server. Use sticky sessions or, better, share sessions with Spring Session (Redis or JDBC).

How can I log out a user from the server side?

With sessions: expire the session in the SessionRegistry or delete it from Redis. With JWT: revoke the refresh token and put the token id on a deny list until it expires.
