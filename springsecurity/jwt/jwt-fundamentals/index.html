JWT Fundamentals: Structure, Signature and Verification

A JSON Web Token (JWT, pronounced 'jot') is a compact, URL-safe string that carries claims (statements about a user) and is protected by a digital signature. The server that receives it can trust the content without looking anything up, because it can verify the signature. Understanding exactly what is inside, what is signed and what is not, is the base for every JWT decision.

signature = SIGN( base64url(header) + "." + base64url(payload) , key )
Anyone can READ header and payload (Base64 is not encryption). Only the key holder can create a valid SIGNATURE.
  • Base64url is an encoding to make bytes printable and URL safe (uses - and _ instead of + and /, no = padding). It hides nothing.
  • The signature covers the header and the payload. Changing even one character makes verification fail.
  • A JWT is a bearer token: whoever holds it can use it. There is no link to the client that received it (unless you add one, see the hardening page).

Custom claims (roles, tenantId, email) are allowed. Keep them few and small, because the token is sent with every request.

JWS, JWE and JWT: the words

TermMeaning
JWTThe token format (claims as JSON)
JWS (JSON Web Signature)A JWT that is SIGNED. Content readable, integrity protected. This is what almost everybody means by JWT
JWE (JSON Web Encryption)A JWT that is ENCRYPTED. Content hidden from everyone without the key (5 parts). Use when claims are sensitive
JWK / JWKSJSON format for keys / a set of public keys published at an URL (for example /.well-known/jwks.json)

Signing algorithms

AlgorithmTypeHowUse
HS256 / HS384 / HS512Symmetric (HMAC)One shared secret signs AND verifiesOne service both issues and verifies. Any verifier can also forge tokens
RS256 / RS384 / RS512Asymmetric (RSA)Private key signs, public key verifiesStandard for distributed systems. Verifiers cannot forge tokens
ES256 / ES384Asymmetric (ECDSA)Private key signs, public key verifies. Smaller keys and signatures than RSAModern choice, fast verification

Verification: the exact steps a resource server does

1. Split the token into 3 parts. Reject if the format is wrong.
2. Read the header: alg and kid.  (the ALGORITHM must be one YOU allow, never blindly trust the header)
3. Find the key for kid (from the JWKS) or use the configured key.
4. Recompute the signature over base64(header).base64(payload) and compare with constant-time equality.   ─► mismatch: reject (401)
5. Only NOW read the claims:
      exp in the future?  nbf in the past?  iss equals the expected issuer?  aud contains this API?
6. Map claims to Authentication (sub -> name, scope/roles -> authorities).
Rule: never trust or use any claim before the signature has been verified.

Runnable example: create, read and tamper with a JWT (plain Java, no library)

This program builds an HS256 token by hand, decodes it, then changes the role to ADMIN without the key. The forged token fails verification. It was executed, and the output below is real.

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.Base64;
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

public class Main {
    static final byte[] SECRET = "this-is-a-demo-secret-of-32-bytes!".getBytes(StandardCharsets.UTF_8);

    static String b64(byte[] b) { return Base64.getUrlEncoder().withoutPadding().encodeToString(b); }
    static String text(String b64) { return new String(Base64.getUrlDecoder().decode(b64), StandardCharsets.UTF_8); }

    static String sign(String signingInput) throws Exception {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(SECRET, "HmacSHA256"));
        return b64(mac.doFinal(signingInput.getBytes(StandardCharsets.UTF_8)));
    }

    static boolean verify(String jwt) throws Exception {
        String[] p = jwt.split("\\.");
        String expected = sign(p[0] + "." + p[1]);
        return MessageDigest.isEqual(expected.getBytes(StandardCharsets.UTF_8), p[2].getBytes(StandardCharsets.UTF_8));   // constant time
    }

    public static void main(String[] args) throws Exception {
        String header = "{\"alg\":\"HS256\",\"typ\":\"JWT\"}";
        String payload = "{\"sub\":\"ram\",\"roles\":[\"USER\"],\"iat\":1790000000,\"exp\":1790000900}";
        String signingInput = b64(header.getBytes(StandardCharsets.UTF_8)) + "." + b64(payload.getBytes(StandardCharsets.UTF_8));
        String jwt = signingInput + "." + sign(signingInput);

        System.out.println("JWT      : " + jwt);
        String[] parts = jwt.split("\\.");
        System.out.println("header   : " + text(parts[0]));
        System.out.println("payload  : " + text(parts[1]));

        String forgedPayload = b64("{\"sub\":\"ram\",\"roles\":[\"ADMIN\"],\"iat\":1790000000,\"exp\":1790000900}".getBytes(StandardCharsets.UTF_8));
        String forged = parts[0] + "." + forgedPayload + "." + parts[2];
        System.out.println("original token valid : " + verify(jwt));
        System.out.println("forged (ADMIN) valid : " + verify(forged));
    }
}

Stateless authentication: the idea

SESSION                                              JWT
Server stores: sessionId ─► {user, roles, ...}       Server stores: nothing
Browser stores: sessionId                            Client stores: the token itself (all data inside, signed)
Each request: server looks up the session            Each request: server verifies the signature and reads the claims
Revoke: delete the session (instant)                 Revoke: hard (the token is valid until exp)

Common mistake: Believing that the JWT payload is secret because it looks like random text. It is only Base64 encoded. Never put passwords, personal data or secrets in it, or encrypt it with JWE.

Interview questions

What is inside a JWT?

A header (algorithm and key id), a payload with claims (sub, exp, roles ...) and a signature over both. The first two parts are readable by anyone.

What does the signature protect?

Integrity and origin: nobody without the key can change the claims or create a valid token. It does not hide the content and does not stop a stolen token from being used.

Why should the server not trust the alg header?

The attacker controls the header. If the server obeys alg=none or switches from RS256 to HS256, verification can be bypassed. The server must decide which algorithm it accepts.
