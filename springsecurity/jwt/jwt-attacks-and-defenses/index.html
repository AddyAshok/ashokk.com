JWT Attacks and Defenses

Real attacks against JWT implementations happen because of validation mistakes, not because the cryptography is broken. Knowing each attack tells you which check must never be skipped.

Attack overview

AttackHow it worksDefense
alg=noneAttacker sets alg to none and removes the signature. A weak library accepts itPin accepted algorithms. Modern Spring/Nimbus rejects none
Algorithm confusion (RS256 to HS256)Server expects RS256. Attacker signs with HS256 using the PUBLIC key as the HMAC secret. A library that trusts the alg header verifies it with the public key as a secret and accepts the tokenFix the algorithm per key. withPublicKey(...).signatureAlgorithm(RS256)
Weak HMAC secretAttacker takes a token and brute forces the secret offline (hashcat) like 'secret' or 'password123'Random secret of 256 bits or more, or use asymmetric keys
Payload tamperingChange roles in the payload and hope the signature is not checkedAlways verify. Never use decode-only APIs for authorization
kid injectionThe kid header is used in a file path or SQL query: '../../dev/null' or a SQL payload selects a known keyTreat kid as untrusted. Look it up in an allow-list of keys (map), never in a raw query or path
jku / x5u / jwk header injectionHeader tells the server where to fetch the key. Attacker points it to his own server with his own keyIgnore these headers. Configure the JWKS URI on the server side only
Missing audience check (token confusion)A token issued for service A is accepted by service BValidate aud in every service, separate audiences and scopes
Missing issuer checkTokens from another (attacker controlled) issuer acceptedValidate iss. Use issuer-uri
No expiry check or huge lifetimeA stolen token works foreverAlways exp, short lifetimes
Token theft (XSS, logs, URL)Attacker copies a valid tokenSafe storage, CSP, HTTPS, no tokens in URLs or logs, short expiry, binding
ReplayCaptured token is sent againHTTPS, short exp, jti tracking for one-time tokens (email links), DPoP
Refresh token theftLong-lived credential stolenRotation and reuse detection, HttpOnly cookie, bind to device
Timing attacksSignature comparison leaks information through timeUse library verification with constant-time comparison
Sensitive data in payloadAnyone reads itMinimal claims, JWE

Algorithm confusion in detail

Server config (vulnerable library):  verify(token, key = PUBLIC_KEY)   and reads the algorithm from the token header
Attacker (knows the public key: it is public!):
   header  = { "alg": "HS256" }               ◄── changed from RS256
   payload = { "sub": "admin", "roles": ["ADMIN"] }
   signature = HMAC-SHA256( header.payload , secret = the PUBLIC KEY bytes )
Server:  alg says HS256 ─► uses the configured key as an HMAC secret ─► signature matches ─► attacker is admin.
Fix: the server decides the algorithm from ITS OWN configuration: RSA public key can only be used with RS256/ES256, never as an HMAC secret.
// SAFE in Spring Security: the key type decides the verifier and the algorithm is pinned
NimbusJwtDecoder.withPublicKey(rsaPublicKey).signatureAlgorithm(SignatureAlgorithm.RS256).build();
// ALSO SAFE: jwk-set-uri with jws-algorithms=RS256, keys selected by kid from YOUR JWKS only

Decode is not verify

// DANGEROUS: only decodes. Anyone can craft a payload
String payload = new String(Base64.getUrlDecoder().decode(token.split("\\.")[1]));
if (payload.contains("\"role\":\"ADMIN\"")) { grantAdmin(); }            // NEVER

// CORRECT: verify first (throws JwtException when signature, exp, iss or aud are wrong)
Jwt jwt = jwtDecoder.decode(token);
if (jwt.getClaimAsStringList("authorities").contains("ROLE_ADMIN")) { grantAdmin(); }

Weak secret cracking: why HS256 needs a strong secret

The signature is public. An attacker who has one token can test guesses offline at billions per second: compute HMAC(guess, header.payload) and compare with the signature. A secret such as 'secret' or a company name is found in seconds. A random 256-bit value is impossible to guess. Generate it with a secure generator, for example: openssl rand -base64 32.

openssl rand -base64 32                       # a good HS256 secret
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private.pem
openssl rsa -in private.pem -pubout -out public.pem
openssl genpkey -algorithm ed25519 -out ed-private.pem

Write negative tests for your validation

@SpringBootTest
class JwtValidationTest {

    @Autowired JwtDecoder decoder;
    @Autowired JwtEncoder encoder;
    @Autowired RSAKey rsaKey;

    private String token(Duration lifetime, String audience, String issuer) {
        Instant now = Instant.now();
        JwtClaimsSet claims = JwtClaimsSet.builder().issuer(issuer).audience(List.of(audience)).subject("1")
                .issuedAt(now).expiresAt(now.plus(lifetime)).id(UUID.randomUUID().toString()).build();
        return encoder.encode(JwtEncoderParameters.from(JwsHeader.with(SignatureAlgorithm.RS256).keyId(rsaKey.getKeyID()).build(), claims)).getTokenValue();
    }

    @Test void validTokenPasses() { assertDoesNotThrow(() -> decoder.decode(token(Duration.ofMinutes(5), "shop-api", "https://auth.shop.example"))); }
    @Test void expiredIsRejected() { assertThrows(JwtValidationException.class, () -> decoder.decode(token(Duration.ofMinutes(-5), "shop-api", "https://auth.shop.example"))); }
    @Test void wrongAudienceIsRejected() { assertThrows(JwtValidationException.class, () -> decoder.decode(token(Duration.ofMinutes(5), "other-api", "https://auth.shop.example"))); }
    @Test void wrongIssuerIsRejected() { assertThrows(JwtValidationException.class, () -> decoder.decode(token(Duration.ofMinutes(5), "shop-api", "https://evil.example"))); }

    @Test
    void tamperedPayloadIsRejected() {
        String[] p = token(Duration.ofMinutes(5), "shop-api", "https://auth.shop.example").split("\\.");
        String forged = p[0] + "." + Base64.getUrlEncoder().withoutPadding().encodeToString("{\"sub\":\"admin\"}".getBytes()) + "." + p[2];
        assertThrows(JwtException.class, () -> decoder.decode(forged));
    }

    @Test
    void noneAlgorithmIsRejected() {
        String header = Base64.getUrlEncoder().withoutPadding().encodeToString("{\"alg\":\"none\"}".getBytes());
        String payload = Base64.getUrlEncoder().withoutPadding().encodeToString("{\"sub\":\"admin\"}".getBytes());
        assertThrows(JwtException.class, () -> decoder.decode(header + "." + payload + "."));
    }
}

Checklist against JWT attacks

  • Pinned algorithm, asymmetric keys, strong secrets.
  • Validate signature, exp, nbf, iss and aud on every request in every service.
  • Never trust headers that point to keys (jku, x5u, jwk) and treat kid as untrusted input.
  • Short lifetimes, refresh rotation, revocation options.
  • Safe storage and CSP against XSS. Tokens never in URLs or logs.
  • Use maintained libraries (Nimbus via Spring Security), keep them updated, and write negative tests.

Common mistake: Writing your own JWT parser or verifying only the signature. Every skipped check (exp, iss, aud, algorithm) is a known attack. Use the framework decoder with validators and test the negative cases.

Interview questions

What is the JWT algorithm confusion attack?

The attacker changes alg from RS256 to HS256 and signs with the public key as the HMAC secret. If the server picks the algorithm from the token header, it accepts the forged token. Pinning the algorithm prevents it.

Why is the kid header dangerous?

It is attacker controlled. If the server uses it in a file path or SQL query, it leads to path traversal or injection, or to selecting a key the attacker knows. Look it up only in a fixed set of your own keys.

Can someone read my JWT payload?

Yes, anyone holding the token can. Signing prevents changes, not reading. Keep sensitive data out or use JWE.
