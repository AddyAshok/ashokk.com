Making JWT More Secure: Complete Hardening Guide

A default JWT setup already works, but it is not yet safe enough for important data. Each topic below removes one real risk: weak keys, wrong algorithms, missing validation, theft, no revocation and stale permissions. Apply as many as your risk level requires.

Hardening overview

#RiskMeasure
1Forged tokensAsymmetric signing (RS256, ES256, EdDSA) and a pinned algorithm
2Key leak or old keyKey ids (kid), JWKS, regular rotation, private key in a vault
3Token for another service or issuerValidate iss and aud, and give every API its own audience
4Long window of misuse after theftShort access token lifetime (5 to 15 minutes)
5Refresh token theftOpaque refresh tokens, hashed in DB, rotation, reuse detection
6No logout, no emergency stopDeny list by jti, per-user token version, revoke refresh tokens
7Stale rolesShort lifetime, token version, re-check sensitive actions in the database
8XSS steals the tokenDo not keep tokens in localStorage. Memory or HttpOnly cookie, BFF pattern, CSP
9Stolen token used from another deviceToken binding with a fingerprint cookie, or DPoP / mTLS
10Data exposureMinimal claims, no personal data, JWE if needed
11Leaks in logs and URLsHeader only, never in URLs, mask Authorization in logs
12Brute force and abuseRate limit login and refresh, alert on anomalies

1. Asymmetric signing and a pinned algorithm

NimbusJwtDecoder decoder = NimbusJwtDecoder
        .withPublicKey(publicKey)
        .signatureAlgorithm(SignatureAlgorithm.RS256)      // only this algorithm. "none" and HS256 are rejected
        .build();
// With HS256 the secret must be a random value of at least 256 bits (32 bytes), never a dictionary word, and known only to ONE service.

2. Key rotation with kid and JWKS

Auth server publishes:  GET /.well-known/jwks.json   { "keys": [ {kid: "k2026-09", ...public}, {kid: "k2026-06", ...public} ] }
Token header:           { "alg": "RS256", "kid": "k2026-09" }
Rotation:  1. create the new key k2026-12 and add its PUBLIC part to the JWKS
           2. start signing with k2026-12
           3. keep the old public key in the JWKS until all old tokens have expired (max token lifetime)
           4. remove the old key
Resource servers use jwk-set-uri: they cache the keys and reload when they see an unknown kid, so rotation needs no redeploy.
spring.security.oauth2.resourceserver.jwt.jwk-set-uri=https://auth.shop.example/.well-known/jwks.json
spring.security.oauth2.resourceserver.jwt.jws-algorithms=RS256
// Expose the public keys from your own auth server
@RestController
class JwksController {
    private final RSAKey rsaKey;
    JwksController(RSAKey rsaKey) { this.rsaKey = rsaKey; }

    @GetMapping("/.well-known/jwks.json")
    Map<String, Object> jwks() { return new JWKSet(rsaKey.toPublicJWK()).toJSONObject(); }   // toPublicJWK: never the private part
}

3. Full validation: time, issuer, audience, revocation

@Bean
public JwtDecoder jwtDecoder(RSAKey rsaKey, TokenRevocationService revocation) throws JOSEException {
    NimbusJwtDecoder decoder = NimbusJwtDecoder.withPublicKey(rsaKey.toRSAPublicKey())
            .signatureAlgorithm(SignatureAlgorithm.RS256).build();

    OAuth2TokenValidator<Jwt> timestamp = new JwtTimestampValidator(Duration.ofSeconds(30));    // exp / nbf with 30 s clock skew
    OAuth2TokenValidator<Jwt> issuer = new JwtIssuerValidator("https://auth.shop.example");
    OAuth2TokenValidator<Jwt> audience = new JwtClaimValidator<List<String>>(
            JwtClaimNames.AUD, aud -> aud != null && aud.contains("shop-api"));                    // this token is FOR this API
    OAuth2TokenValidator<Jwt> notRevoked = jwt -> revocation.isRevoked(jwt.getId())
            ? OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "Token has been revoked", null))
            : OAuth2TokenValidatorResult.success();

    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(timestamp, issuer, audience, notRevoked));
    return decoder;
}

4 and 5. Short access tokens, rotating refresh tokens

Keep access tokens at 5 to 15 minutes. Use the refresh token flow (rotation, hashed storage, reuse detection) from the refresh token page, so a stolen access token is useful only for minutes and a stolen refresh token is detected.

6. Revocation: deny list and token version

@Service
public class TokenRevocationService {

    private final StringRedisTemplate redis;
    public TokenRevocationService(StringRedisTemplate redis) { this.redis = redis; }

    /** Block one token until it would expire anyway. The deny list stays small because entries expire by themselves. */
    public void revoke(Jwt jwt) {
        Duration remaining = Duration.between(Instant.now(), jwt.getExpiresAt());
        if (!remaining.isNegative()) redis.opsForValue().set("jwt:deny:" + jwt.getId(), "1", remaining);
    }

    public boolean isRevoked(String jti) {
        return jti != null && Boolean.TRUE.equals(redis.hasKey("jwt:deny:" + jti));
    }
}

// Logout endpoint: revoke the presented access token and the refresh token
@PostMapping("/auth/logout")
public ResponseEntity<Void> logout(@AuthenticationPrincipal Jwt jwt, @CookieValue(name = "refresh_token", required = false) String refresh) {
    revocation.revoke(jwt);
    if (refresh != null) refreshTokens.revoke(refresh);
    return ResponseEntity.noContent().build();
}

Token version: keep an integer per user (the tokenVersion column). Put it in the token as a claim (ver). At validation compare it with the current value (cache it for a few seconds). Increasing the version instantly invalidates ALL tokens of that user: use it for password change, role change, 'log out from all devices' and account compromise.

OAuth2TokenValidator<Jwt> versionValidator = jwt -> {
    Long userId = Long.valueOf(jwt.getSubject());
    int current = tokenVersionCache.get(userId);                    // Caffeine cache with a 10 second TTL over the database
    Number claimed = jwt.getClaim("ver");
    return claimed != null && claimed.intValue() == current
            ? OAuth2TokenValidatorResult.success()
            : OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "Token version outdated", null));
};

Short expiry onlyAfter exp (minutes)None. Good baseline
Deny list by jtiYesRedis lookup per request. Entries expire with the token

7. Stale roles

  • Accept that roles in a token can be up to (token lifetime) minutes old. For most apps 10 minutes is fine.
  • For dangerous actions (delete account, money transfer, admin operations) check the permission in the database, or require a fresh login (step-up authentication).
  • Or put only the user id in the token and load authorities from a cache on each request (a trade-off: a lookup per request).

8. Where to keep the token in the browser

StorageXSS can steal it?CSRF risk?Verdict
localStorage / sessionStorageYes, easilyNoAvoid for long-lived or powerful tokens
JavaScript memory (variable)Harder, but XSS can still use it while the page runsNoGood for short access tokens, lost on reload
HttpOnly Secure SameSite cookieCannot be read by scripts (but can be used by them)Yes: needs SameSite and a CSRF defenseGood, best for refresh tokens
BFF pattern (backend for frontend)Tokens never reach the browser. Browser has only a session cookieCSRF defense neededStrongest for SPAs

Recommended for a SPA: access token in memory, refresh token in an HttpOnly Secure SameSite=Strict cookie limited to the /auth path, a strict Content-Security-Policy, and no third-party scripts you do not control. With a BFF, tokens stay on the server.

9. Token binding with a fingerprint (stops simple theft)

Login:  server creates a random FINGERPRINT (32 bytes)
        ─► sends it in an HttpOnly Secure cookie  __Secure-Fgp=<fingerprint>
        ─► puts SHA-256(fingerprint) into the JWT claim "fgp"
Each request: the cookie arrives automatically, the token in the header. The validator hashes the cookie and compares with fgp.
Attacker steals the token via XSS or logs: has no fingerprint cookie (HttpOnly, invisible to scripts) ─► token is rejected.
OAuth2TokenValidator<Jwt> fingerprint = jwt -> {
    HttpServletRequest request = ((ServletRequestAttributes) RequestContextHolder.currentRequestAttributes()).getRequest();
    Cookie cookie = WebUtils.getCookie(request, "__Secure-Fgp");
    String claim = jwt.getClaimAsString("fgp");
    if (cookie == null || claim == null || !sha256Hex(cookie.getValue()).equals(claim)) {
        return OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "Fingerprint mismatch", null));
    }
    return OAuth2TokenValidatorResult.success();
};

For stronger sender constraining use DPoP (proof of possession with a per-client key, supported in newer Spring Security versions) or mutual TLS. They make a stolen token useless without the client's private key.

10. Minimal claims

// GOOD
{ "iss":"https://auth.shop.example", "aud":["shop-api"], "sub":"4711", "iat":1790000000, "exp":1790000600,
  "jti":"6f1c...", "ver":3, "scope":"orders:read orders:write" }

// BAD: personal data, secrets, huge lists
{ "sub":"ram", "email":"ram@example.com", "phone":"+91...", "address":"...", "cardNumber":"...", "permissions":[ ...200 entries... ] }

11. Transport and logging

  • HTTPS only, with HSTS. Never send tokens in query strings (they land in browser history, proxy logs and Referer headers).
  • Mask the Authorization header and cookies in access logs and error reports.
  • Return generic errors: invalid_token without details about why.
  • Do not accept tokens from cookies and headers at the same time without thinking about which one wins.

12. Abuse control and monitoring

  • Rate limit /auth/login and /auth/refresh per IP and per account.
  • Alert on refresh token reuse, many 401 with invalid_token, tokens with unknown kid, and logins from new countries.
  • Log security events: token issued, refreshed, revoked, validation failures (without the token itself).

Hardened token lifecycle summary

login (rate limited, lockout, MFA)  ─► access JWT (RS256, kid, iss, aud, 10 min, jti, ver, fgp) + refresh token (opaque, hashed, 7 days, rotating, HttpOnly cookie)
each API call                        ─► verify signature (pinned alg) ─► exp/nbf ─► iss ─► aud ─► not on deny list ─► ver current ─► fingerprint
refresh                              ─► rotate; reuse of an old refresh token ─► revoke everything for the user ─► alert
logout / password change / incident  ─► revoke refresh tokens, deny-list jti, bump token version
key rotation                         ─► new kid in JWKS, old public key kept until old tokens expire

Common mistake: Adding revocation lists and fingerprints but keeping 24 hour access tokens and localStorage. Security is the weakest link. First fix the basics (short expiry, correct validation, safe storage), then add the advanced controls your risk needs.

Interview questions

What are the top 5 things to do to secure JWT?

Use asymmetric signing with a pinned algorithm, validate exp, iss and aud, keep access tokens short, rotate opaque refresh tokens with reuse detection, and store tokens safely (memory plus HttpOnly cookie or a BFF).

How can I revoke a JWT immediately?

Put its jti on a deny list until it expires, or increase the user's token version so all older tokens fail validation, and revoke the refresh tokens.

Is encrypting the JWT (JWE) needed?

Only if the claims are sensitive. The better rule is to keep sensitive data out of the token and use the token as a key to look up data on the server.
