SQL Generation, JDBC Batching and Bulk Operations

Performance work in JPA means controlling the SQL. This page shows how Hibernate turns JPQL into SQL, the query plan cache, how JDBC batching really works, bulk operations, StatelessSession and the settings that matter.

From JPQL to a result

em.createQuery("select p from Product p where p.category = :c")
  1. QueryInterpretationCache: parsed JPQL (HQL AST) for this string? no ─► parse it, build the semantic model (SQM), store it   (plan cache)
  2. SQL AST + dialect ─► the SQL string  (for example "select p1_0.id,p1_0.name ... from products p1_0 where p1_0.category=?")
  3. PreparedStatement from the connection, bind parameters
  4. ResultSet ─► JdbcValuesSourceProcessingState ─► entities are looked up in the persistence context first, created if new, hydrated
Cache keys are the query STRINGS: concatenating values into the query string creates a new plan every time and can exhaust memory (use parameters).
SettingMeaning
hibernate.query.plan_cache_max_sizeNumber of cached query plans (default 2048)
hibernate.query.in_clause_parameter_paddingIN (?,?,?) lists padded to sizes 1,2,4,8,16.. so fewer distinct SQL strings/plans
hibernate.jdbc.fetch_sizeRows per network fetch of the JDBC driver (PostgreSQL only streams with autocommit off + fetch size)
hibernate.jdbc.batch_sizeStatements sent together
hibernate.order_inserts / order_updatesSort by entity type so equal statements are adjacent
hibernate.jdbc.batch_versioned_dataBatch updates of @Version entities (true by default in modern versions)
hibernate.connection.handling_modeWhen the session gives back the connection (DELAYED_ACQUISITION_AND_RELEASE_AFTER_TRANSACTION is the default with JPA)

JDBC batching in action

@Transactional
public void importProducts(List<ProductDto> dtos) {
    for (int i = 0; i < dtos.size(); i++) {
        em.persist(new Product(dtos.get(i)));              // SEQUENCE id: nothing sent yet, INSERT queued in the ActionQueue
        if (i > 0 && i % 50 == 0) {
            em.flush();                                    // 50 INSERTs sent as ONE JDBC batch (executeBatch)
            em.clear();                                    // detach the 50 entities: memory and dirty checking stay small
        }
    }
}
Requirement for real batchingWhy
hibernate.jdbc.batch_size > 0Enables the batch
ID generation SEQUENCE (not IDENTITY)IDENTITY forces an immediate INSERT for each entity
order_inserts/order_updates = trueInserts of parent and child alternate otherwise, breaking batches
Driver supports it (PostgreSQL: reWriteBatchedInserts=true in the JDBC URL)The driver turns the batch into one multi-row INSERT
Flush + clear regularlyPrevents an ever growing persistence context
spring.datasource.url=jdbc:postgresql://localhost:5432/shop?reWriteBatchedInserts=true
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true

Check in the SQL log: with batching you see the INSERT once with the bound values per row (or use datasource-proxy which prints 'Batch: true, BatchSize: 50'). With Hibernate statistics look at getJdbcBatchCount / getPrepareStatementCount.

Bulk operations bypass the persistence context

@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update Product p set p.status = 'ARCHIVED' where p.updatedAt < :limit")
int archiveOld(@Param("limit") Instant limit);                     // ONE statement for a million rows. No entities loaded, no callbacks, @Version not increased
WaySpeed for 100,000 rowsNotes
repository.save in a loop, IDENTITY, no batchingSlowestOne round trip per row plus dirty checking
saveAll with SEQUENCE + batching + flush/clearFastStill creates objects
JdbcTemplate.batchUpdate / jdbc batchFasterNo entity overhead
Bulk JPQL update/deleteFastest for changes by conditionOne statement in the database

StatelessSession: no persistence context

SessionFactory sf = emf.unwrap(SessionFactory.class);
try (StatelessSession session = sf.openStatelessSession()) {
    Transaction tx = session.beginTransaction();
    for (ProductDto dto : dtos) {
        session.insert(new Product(dto));           // sent directly. No first level cache, no dirty checking, no cascades, no lazy loading
    }
    tx.commit();
}
// Good for imports and ETL. It bypasses Spring's transaction management: you control the transaction yourself.

Stream large reads

@Transactional(readOnly = true)
public void exportAll(Consumer<Product> sink) {
    try (Stream<Product> stream = repository.streamAll()) {          // streamAll: @QueryHints fetchSize + readOnly
        stream.forEach(p -> { sink.accept(p); em.detach(p); });       // detach after use: memory stays constant
    }
}
// Or use a projection/DTO and JdbcTemplate with a RowCallbackHandler for pure reporting.

Reading the SQL: checklist

  • Are there unexpected extra selects (lazy loading, merge selects, @Formula subqueries)?
  • Is each write batched? Do inserts alternate between tables?
  • Do queries select columns that are not needed (use projections)?
  • Do queries use the indexes (EXPLAIN ANALYZE)? Are there joins to tables not needed for the result?
  • Is there a count query for every page that could use Slice?

Common mistake: Loading 100,000 entities and calling save in a loop inside one transaction with IDENTITY ids. Memory and dirty checking grow with every entity and no batching happens. Use SEQUENCE ids, batching with flush and clear, or bulk and JDBC operations.

Interview questions

Why does hibernate.jdbc.batch_size seem to have no effect?

Typical reasons: IDENTITY ids, order_inserts not enabled with parent and child inserts, or the driver not rewriting batches. Verify with a batch logger or statistics.

Why should I flush and clear in import loops?

Without clear(), every persisted entity stays in the persistence context, memory grows and each flush scans them all for dirty checking, so the loop gets slower and slower.

Is a bulk update safe?

It is fast, but it bypasses entities, callbacks, cascades and @Version, and the persistence context may hold stale objects. Use clearAutomatically and be aware of what it skips.
