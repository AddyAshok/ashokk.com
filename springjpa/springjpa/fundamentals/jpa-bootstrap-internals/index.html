JPA Bootstrap Internals: EntityManagerFactory, EntityManager and Sessions

Before your first repository call, Spring Boot and Hibernate do a lot of work at startup. Knowing the objects involved (EntityManagerFactory, EntityManager, Session, shared EntityManager proxy) explains thread safety, lifecycle and why some errors appear at startup.

Startup workflow

Spring Boot startup
  1. DataSourceAutoConfiguration       ─► HikariDataSource bean
  2. HibernateJpaAutoConfiguration     ─► JpaProperties, HibernateProperties, JpaVendorAdapter (HibernateJpaVendorAdapter)
  3. LocalContainerEntityManagerFactoryBean  (Spring's FactoryBean, needs DataSource + packagesToScan)
        ├─ scans packages for @Entity, @Embeddable, @MappedSuperclass  (PersistenceUnitInfo, no persistence.xml needed)
        └─ asks Hibernate to build the SessionFactory:
              a. read annotations ─► Metadata (entities, tables, columns, relations, generators)
              b. resolve dialect, types, naming strategies
              c. build query plans for @NamedQuery and validate them
              d. run schema tool per ddl-auto (validate / update / create ...)
              e. prepare proxies (ByteBuddy), caches, event listeners
        Result: EntityManagerFactory (= SessionFactory)      ONE per database, thread safe, expensive, lives as long as the application
  4. JpaTransactionManager             ─► bound to the EntityManagerFactory
  5. JpaRepositoriesAutoConfiguration  ─► repository proxies (next topics)
Errors at startup: unknown property in @Query or query method, wrong mapping, missing column with ddl-auto=validate.

Why can I inject one EntityManager into a singleton?

An EntityManager is not thread safe, but a Spring singleton is shared by all threads. Spring solves this with a shared EntityManager proxy: @PersistenceContext (or constructor injection of EntityManager) injects a proxy created by SharedEntityManagerCreator. Each method call on the proxy looks up the EntityManager bound to the CURRENT transaction (thread) and delegates to it.

@Service class ReportService { @PersistenceContext EntityManager em; }     em is a PROXY (same object for all threads)

thread A: @Transactional method ─► JpaTransactionManager opens Session A and binds it to thread A (TransactionSynchronizationManager)
          em.find(...)  ─► proxy asks "which EntityManager is bound to my thread?"  ─► Session A
thread B: @Transactional method ─► Session B ...
No transaction active: the proxy creates a temporary EntityManager for ONE call and closes it afterwards.
   So entities returned outside a transaction are DETACHED at once, and lazy loading fails.
@Service
public class ProductQueryService {

    private final EntityManager em;                             // constructor injection works too (Spring provides the shared proxy)

    public ProductQueryService(EntityManager em) { this.em = em; }

    @Transactional(readOnly = true)
    public List<Product> cheap(BigDecimal max) {
        return em.createQuery("select p from Product p where p.price < :max", Product.class)
                 .setParameter("max", max)
                 .getResultList();
    }
}

Get the Hibernate Session when you need Hibernate features

Session session = em.unwrap(Session.class);                 // Hibernate API behind the JPA API
session.setDefaultReadOnly(true);                             // stop dirty checking for everything loaded in this session
session.enableFilter("tenantFilter").setParameter("tenantId", 7L);
SessionFactory sf = emf.unwrap(SessionFactory.class);         // statistics, cache management

Transaction and EntityManager scope: the modes

ModeHowNotes
Transaction-scoped (Spring default)EntityManager lives for the transaction. Detached after commitRecommended
Extended (open-in-view)EntityManager kept open for the whole HTTP requestspring.jpa.open-in-view=true. Hides lazy problems. Avoid
Application-managedemf.createEntityManager() and you close it yourselfBatch tools, special cases. You must handle transactions and close it
// Application-managed EntityManager (rare): you own the lifecycle
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();
try {
    tx.begin();
    em.persist(new Product("Pen", BigDecimal.TEN, "office"));
    tx.commit();
} catch (RuntimeException e) {
    if (tx.isActive()) tx.rollback();
    throw e;
} finally {
    em.close();
}

Common mistake: Storing an EntityManager (or entities loaded from it) in a field of a singleton or passing it to another thread. The shared proxy is safe, but a real Session is not thread safe. Never use a Session or managed entities across threads.

Interview questions

Is EntityManagerFactory expensive to create?

Yes. It parses all mappings and builds metadata, so it is created once at startup and shared. EntityManagers are cheap and short lived.

What does @PersistenceContext really inject?

A shared EntityManager proxy. It delegates to the EntityManager of the current transaction, or to a temporary one if no transaction is active.

Why do entities become detached after the service method?

The transaction-scoped EntityManager is closed at commit. The objects survive as plain Java objects, but changes are no longer tracked and lazy fields cannot load.
