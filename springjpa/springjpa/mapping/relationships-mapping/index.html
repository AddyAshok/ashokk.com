Relationship Mapping: One-to-One, One-to-Many, Many-to-Many

Relationships are the source of most JPA bugs and performance problems. This page shows every mapping with the SQL it produces, which side owns the foreign key, how to keep both sides in sync, and the correct cascade and orphan settings.

Key ideas

TermMeaning
Owning sideThe side that has the @JoinColumn (foreign key column). Only changes on the owning side are written to the database
Inverse sideThe side with mappedBy. Read only for the database, but you must keep it in sync in memory
UnidirectionalOnly one entity knows the other (Order has customer). Simpler, fewer bugs
BidirectionalBoth entities have a reference. Needs helper methods to stay in sync
CascadeApply persist, merge, remove, refresh, detach from parent to children
orphanRemovalDelete a child when it is removed from the parent's collection

Many-to-one (the most common and best mapping)

@Entity @Table(name = "orders")
public class OrderEntity {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)          // EAGER is the default for ToOne: always write LAZY
    @JoinColumn(name = "customer_id", nullable = false, foreignKey = @ForeignKey(name = "fk_orders_customer"))
    private Customer customer;
}
// SQL: orders(id, customer_id FK)   Many orders point to one customer.

One-to-many, bidirectional, with helper methods

@Entity
public class Customer {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
    private String name;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderEntity> orders = new ArrayList<>();

    public void addOrder(OrderEntity o) { orders.add(o); o.setCustomer(this); }        // both sides
    public void removeOrder(OrderEntity o) { orders.remove(o); o.setCustomer(null); }
    public List<OrderEntity> getOrders() { return Collections.unmodifiableList(orders); }   // force use of the helpers
}

A unidirectional @OneToMany without mappedBy (only the parent knows children) makes Hibernate use a join table, or extra UPDATE statements for the foreign key: avoid it. Prefer @ManyToOne on the child, and add the @OneToMany side only when you really navigate from the parent.

One-to-one

// Foreign key in the owner table
@Entity public class User {
    @Id @GeneratedValue private Long id;
    @OneToOne(fetch = FetchType.LAZY, cascade = CascadeType.ALL, orphanRemoval = true)
    @JoinColumn(name = "profile_id")
    private Profile profile;
}

// Shared primary key (best: no extra column, load by id)
@Entity public class Profile {
    @Id private Long id;
    @OneToOne(fetch = FetchType.LAZY) @MapsId @JoinColumn(name = "id")
    private User user;
}

The inverse side of a @OneToOne (mappedBy) cannot be lazy in practice: Hibernate has to query the other table to know whether the row exists (null or proxy). Use the shared primary key mapping and load the profile by id when needed.

Many-to-many

@Entity public class Student {
    @Id @GeneratedValue private Long id;
    @ManyToMany
    @JoinTable(name = "student_course", joinColumns = @JoinColumn(name = "student_id"), inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set<Course> courses = new HashSet<>();                  // use SET: a List (bag) deletes and reinserts ALL rows on change

    public void enroll(Course c) { courses.add(c); c.getStudents().add(this); }
}
@Entity public class Course {
    @Id @GeneratedValue private Long id;
    @ManyToMany(mappedBy = "courses") private Set<Student> students = new HashSet<>();
    public Set<Student> getStudents() { return students; }
}
// NEVER use CascadeType.REMOVE or ALL on @ManyToMany: deleting a student would delete shared courses.

When the relationship has its own data (date, grade, status), model it as a third entity (Enrollment) with two @ManyToOne, see the advanced mapping page.

Cascade types

TypeEffect on childrenTypical use
PERSISTpersist(parent) also persists new childrenOwned children
MERGEmerge(parent) also merges childrenOwned children
REMOVEremove(parent) removes childrenOwned children only (order lines)
REFRESH / DETACHPropagate refresh and detachRare
ALLAll of the aboveComposition: child cannot live without the parent
orphanRemoval = trueRemoving a child from the collection deletes its rowComposition

What SQL does adding a child produce?

@Transactional
public void addOrder(Long customerId) {
    Customer c = customers.findById(customerId).orElseThrow();       // select customer
    c.addOrder(new OrderEntity("Laptop"));                            // orders.add(...): the collection is initialized first!  select orders where customer_id=?
}                                                                     // flush: insert into orders (customer_id, item)  (cascade PERSIST)
// Loading a big collection just to add one child is wasteful. Better: orders.save(new OrderEntity(customers.getReferenceById(id), "Laptop")) : no select of the collection

Design rules

  • All ToOne relations LAZY. Collections are lazy by default.
  • Prefer unidirectional @ManyToOne. Add the collection side only when needed, then keep both sides in sync.
  • Use Set for @ManyToMany. Use List for ordered @OneToMany with @OrderBy or @OrderColumn.
  • Cascade only for real ownership (composition).
  • Do not expose entities in the API: bidirectional relations create infinite JSON recursion.

Common mistake: Marking a @ManyToMany with CascadeType.ALL or REMOVE. Deleting one side deletes the shared other side and its links. Cascade REMOVE and orphanRemoval belong to parent-child ownership only.

Interview questions

Which side owns a bidirectional relationship?

The side without mappedBy, the one that has the @JoinColumn (the @ManyToOne side for one-to-many). Only that side updates the foreign key.

Why is List a problem in @ManyToMany?

A List without an order column is a bag. When an element is removed, Hibernate deletes all link rows and reinserts the remaining ones. A Set only deletes the removed row.

Why is my lazy @OneToOne loaded eagerly?

The inverse side (mappedBy) must check for existence, so Hibernate loads it at once. Put the foreign key or @MapsId on the side you load, or fetch it with a query.
