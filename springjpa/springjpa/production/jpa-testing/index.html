Testing JPA: @DataJpaTest, Testcontainers and Query Counting

Repository and mapping code must be tested against a real database of the same type as production. This page shows the slice test, Testcontainers setup, test data strategies, transaction behavior in tests, and tests that fail on N+1 problems.

@DataJpaTest: the slice

@DataJpaTest starts only:  DataSource (embedded by default), EntityManagerFactory, entities, Spring Data repositories, TestEntityManager, Flyway if present
It does NOT start:  controllers, services, security, Kafka ...
Every test method runs inside a transaction that is ROLLED BACK at the end (data does not leak between tests).
By default it replaces your DataSource with an embedded H2 database: dangerous when production uses PostgreSQL (different SQL, types, locking).
@DataJpaTest
class ProductRepositoryTest {

    @Autowired ProductRepository repository;
    @Autowired TestEntityManager em;

    @Test
    void findsProductsInRange() {
        em.persist(new Product("A", new BigDecimal("10"), "books"));
        em.persist(new Product("B", new BigDecimal("50"), "books"));
        em.persist(new Product("C", new BigDecimal("90"), "toys"));
        em.flush();                                                    // send SQL now
        em.clear();                                                    // empty the persistence context: force a real SELECT

        List<Product> result = repository.inRange("books", new BigDecimal("20"), new BigDecimal("60"));

        assertThat(result).extracting(Product::getSku).containsExactly("B");
    }
}

Always flush() and clear() before the query under test. Otherwise the query may return the objects from the first level cache and hide mapping or SQL errors.

Use the real database with Testcontainers

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)      // keep the real DataSource
@Testcontainers
class ProductRepositoryPostgresTest {

    @Container
    @ServiceConnection                                                              // Boot wires the datasource to the container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");

    @Autowired ProductRepository repository;

    @Test
    void jsonbAndConstraintsWorkLikeInProduction() { /* ... */ }
}
// Share ONE container between test classes: put it in an abstract base class or use a singleton container / reuse to keep the build fast.
# src/test/resources/application-test.properties
spring.jpa.hibernate.ddl-auto=validate          # Flyway creates the schema, the test proves that entities match it
spring.flyway.enabled=true
spring.jpa.properties.hibernate.generate_statistics=true

Transactions in tests

SituationBehavior
@DataJpaTest / @Transactional testOne transaction per test, rollback at the end. Commit-time behavior (constraint checks, afterCommit, flush errors) is NOT exercised unless you flush()
@SpringBootTest without @TransactionalEach repository call commits. You must clean up data yourself
MockMvc test with @TransactionalSame thread: controller and test share the transaction. Not so with RANDOM_PORT clients
@Commit / @Rollback(false)Keep the data of a test
@Test
void uniqueConstraintIsEnforced() {
    repository.saveAndFlush(new Product("SKU-1", "A", BigDecimal.ONE));
    assertThrows(DataIntegrityViolationException.class,
            () -> repository.saveAndFlush(new Product("SKU-1", "B", BigDecimal.TEN)));       // flush is needed to hit the database
}

Make N+1 a test failure

@DataJpaTest
@Import(QueryCounter.class)
class OrderQueryCountTest {
    @Autowired OrderRepository orders;
    @Autowired TestEntityManager em;
    @Autowired EntityManagerFactory emf;

    @Test
    void listWithCustomerNeedsOneQuery() {
        // arrange 20 orders with different customers ...
        em.flush(); em.clear();
        Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
        stats.setStatisticsEnabled(true);
        stats.clear();

        orders.findAllWithCustomer().forEach(o -> o.getCustomer().getName());

        assertThat(stats.getPrepareStatementCount()).isEqualTo(1);           // a lazy N+1 would be 21
    }
}

Test the mapping and schema itself

  • With ddl-auto=validate and Flyway, every test start proves that entities match the migrations.
  • Test that a delete with cascade removes children and orphans, and that soft delete filters work.
  • Test optimistic locking with two transactions (two threads or two EntityManagers) expecting ObjectOptimisticLockingFailureException.
  • Test custom queries with edge data: nulls, empty collections, duplicates, big pages.

Common mistake: Testing repositories only against H2 while production runs PostgreSQL or MySQL. Differences in SQL dialect, types, locking and constraints show up only in production. Use Testcontainers with the same database type.

Interview questions

Why did my repository test pass but the query fails in production?

Probably H2 hides a difference, or the first level cache returned objects without running the query. Use a real database and call flush() and clear() before the assertion.

Why does @DataJpaTest roll back my data?

Each test runs in a transaction that is rolled back at the end, to keep tests independent. Use @Commit or @Rollback(false) only when needed.

How do I speed up Testcontainers tests?

Share one container across test classes (static singleton or base class), enable container reuse locally, and keep slice tests small.
