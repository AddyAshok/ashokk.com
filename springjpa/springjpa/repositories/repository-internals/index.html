Repository Internals: Proxies, SimpleJpaRepository and Query Creation

You never write repository implementations, so where does the code come from? This page follows the complete path: repository scanning, the factory bean, the proxy with its interceptor chain, the query lookup strategy and how method names become JPA queries.

From interface to bean

@EnableJpaRepositories  (Spring Boot: JpaRepositoriesAutoConfiguration)
  └─ JpaRepositoriesRegistrar ─► RepositoryConfigurationExtensionSupport scans base packages for interfaces extending Repository
        for each interface:  BeanDefinition of JpaRepositoryFactoryBean<ProductRepository, Product, Long>
                                 (properties: repositoryInterface, entityManager, queryLookupStrategy, repositoryBaseClass, fragments)
At bean creation (JpaRepositoryFactoryBean.afterPropertiesSet):
  1. JpaRepositoryFactory
  2. RepositoryMetadata: domain type Product, id type Long, which methods are CRUD, which are query methods
  3. RepositoryInformation: which method is served by which part (base class, fragment, query method)
  4. target = new SimpleJpaRepository<>(Product.class, entityManager)         (the real implementation of CRUD methods)
  5. ProxyFactory (JDK dynamic proxy of ProductRepository) with target and this ADVICE CHAIN:
        ├─ ExposeInvocationInterceptor
        ├─ DefaultMethodInvokingMethodInterceptor           (default methods on the interface)
        ├─ RepositoryFragmentsMethodInterceptor             (custom fragment implementations)
        ├─ TransactionInterceptor                           (@Transactional(readOnly=true) on SimpleJpaRepository)
        ├─ PersistenceExceptionTranslationInterceptor       (PersistenceException -> DataAccessException hierarchy)
        ├─ QueryExecutorMethodInterceptor                   (query methods: find derived / @Query / named queries)
        └─ ImplementationMethodExecutionInterceptor         (CRUD methods: invoke on SimpleJpaRepository)
  6. the proxy is the bean you inject

A call through the chain

productRepository.findByCategoryAndPriceGreaterThan("books", 100)
   proxy ─► TransactionInterceptor (join the current tx or start a read-only one)
         ─► PersistenceExceptionTranslationInterceptor
         ─► QueryExecutorMethodInterceptor: find the PRE-BUILT RepositoryQuery for this Method
                PartTreeJpaQuery.execute(parameters):
                    1. create a JPA Criteria/JPQL query object from the PartTree (built once at startup, cached)
                    2. bind the parameters (?1 = "books", ?2 = 100)
                    3. apply Pageable / Sort / limit
                    4. query.getResultList()  ─► Hibernate: SQL ─► JDBC ─► ResultSet ─► managed entities
                    5. convert to the declared return type (List, Optional, Page, projection)

Query lookup strategy: how the query for a method is chosen

StrategyRule
CREATEAlways derive the query from the method name
USE_DECLARED_QUERYUse @Query or a named query. Fail at startup if none exists
CREATE_IF_NOT_FOUND (default)1. @Query on the method 2. named query Entity.methodName 3. derive from the method name

All queries are prepared at startup. A typo (findByNmae) fails the application start with PropertyReferenceException, and a wrong @Query fails with a JPQL syntax error. That is a big advantage over string queries in service code.

PartTree: how a method name is parsed

findByCategoryAndPriceGreaterThanOrderByPriceDesc
   PartTree splits at "By":  subject = "find"        predicate = "CategoryAndPriceGreaterThanOrderByPriceDesc"
   splits the predicate on "OrderBy", then on "Or", then on "And":
        Part(Category, SIMPLE_PROPERTY)     Part(PriceGreaterThan, GREATER_THAN)     Sort(price DESC)
   each Part is resolved against the entity's properties with PropertyPath (Category -> category; CustomerAddressCity tries customerAddressCity,
   then customerAddress.city, then customer.addressCity, then customer.address.city ...)
   ambiguous names: write the underscore  findByCustomer_AddressCity

SimpleJpaRepository: the real implementation (essential parts)

@Repository
@Transactional(readOnly = true)                              // every method is read only unless overridden
public class SimpleJpaRepository<T, ID> implements JpaRepositoryImplementation<T, ID> {

    private final EntityManager entityManager;               // the SHARED EntityManager proxy
    private final JpaEntityInformation<T, ?> entityInformation;

    @Transactional
    public <S extends T> S save(S entity) {
        if (entityInformation.isNew(entity)) { entityManager.persist(entity); return entity; }
        else { return entityManager.merge(entity); }
    }

    public Optional<T> findById(ID id) {
        return Optional.ofNullable(entityManager.find(entityInformation.getJavaType(), id));
    }

    @Transactional
    public void delete(T entity) {
        if (entityInformation.isNew(entity)) return;
        T existing = (T) entityManager.find(ProxyUtils.getUserClass(entity), entityInformation.getId(entity));
        if (existing == null) return;
        entityManager.remove(entityManager.contains(entity) ? entity : entityManager.merge(entity));
    }

    public Page<T> findAll(Pageable pageable) {
        TypedQuery<T> query = getQuery(null, pageable);
        return isUnpaged(pageable) ? new PageImpl<>(query.getResultList())
             : readPage(query, getDomainClass(), pageable, null);         // runs the count query too
    }
}

Where transactions and exceptions come from

  • Reads: readOnly = true means Hibernate uses FlushMode.MANUAL for the session (no dirty checking flush) and the JDBC connection is marked read only when supported.
  • Writes: each write method has its own @Transactional. Without an outer transaction every repository call is its own transaction and commits at once.
  • Exceptions: JPA and Hibernate exceptions become Spring DataAccessException subclasses (DataIntegrityViolationException, OptimisticLockingFailureException, EmptyResultDataAccessException). You do not catch PersistenceException in service code.

Inspect your repository at runtime

@Autowired ProductRepository repository;

System.out.println(repository.getClass());                      // jdk.proxy2.$Proxy123 : the proxy
System.out.println(AopUtils.isJdkDynamicProxy(repository));     // true
System.out.println(AopProxyUtils.ultimateTargetClass(repository)); // class org.springframework.data.jpa.repository.support.SimpleJpaRepository

Fragments composition

interface ProductRepository extends JpaRepository<Product, Long>, ProductRepositoryCustom, AuditSupport
    fragments resolved by name:  ProductRepositoryCustomImpl, AuditSupportImpl     (name = fragment interface + Impl)
    method routing order: user fragments first, then the base class (SimpleJpaRepository), then query methods
    a fragment method with the same signature as a CRUD method OVERRIDES it (for example a custom save)

Common mistake: Adding logic that depends on the concrete repository class (casting the injected repository to SimpleJpaRepository). The bean is a JDK proxy of your interface, so such a cast fails. Use custom fragments or a repository base class.

Interview questions

Is the repository interface implementation created at compile time or at runtime?

At runtime, at startup. Spring Data builds a JDK proxy over SimpleJpaRepository, and prepares all query methods at that moment.

Why does my application fail at startup because of a repository method?

Spring Data validates every query method when the repository is created. An unknown property in the method name or an invalid JPQL string stops the start on purpose.

Are repository methods transactional?

Yes. CRUD reads are readOnly transactions and writes are normal transactions. Derived and @Query methods inherit readOnly from the class level unless you add @Transactional.
