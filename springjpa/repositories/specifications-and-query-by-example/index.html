Dynamic Queries: Specifications, Query by Example, Criteria and Querydsl

Screens with optional filters need queries that are built at runtime. Spring Data offers Specifications (Criteria API based), Query by Example and, with an extra library, Querydsl. This page explains each with complete code and when to choose which.

Specifications

public interface ProductRepository extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> { }

public final class ProductSpecs {
    private ProductSpecs() { }

    public static Specification<Product> nameContains(String text) {
        return (root, query, cb) -> text == null || text.isBlank() ? null
                : cb.like(cb.lower(root.get(Product_.name)), "%" + text.toLowerCase() + "%");   // Product_ is generated (hibernate-jpamodelgen)
    }
    public static Specification<Product> inCategory(Collection<String> categories) {
        return (root, query, cb) -> categories == null || categories.isEmpty() ? null : root.get(Product_.category).in(categories);
    }
    public static Specification<Product> priceBetween(BigDecimal min, BigDecimal max) {
        return (root, query, cb) -> {
            List<Predicate> p = new ArrayList<>();
            if (min != null) p.add(cb.greaterThanOrEqualTo(root.get(Product_.price), min));
            if (max != null) p.add(cb.lessThanOrEqualTo(root.get(Product_.price), max));
            return p.isEmpty() ? null : cb.and(p.toArray(Predicate[]::new));
        };
    }
    public static Specification<Product> hasTag(String tag) {                                 // join on a collection
        return (root, query, cb) -> {
            if (tag == null) return null;
            query.distinct(true);
            return cb.equal(root.join(Product_.tags).get(Tag_.name), tag);
        };
    }
    public static Specification<Product> withSupplier() {                                     // fetch join for the result query only
        return (root, query, cb) -> {
            if (Long.class != query.getResultType()) root.fetch(Product_.supplier, JoinType.LEFT);   // the count query has no fetch
            return null;
        };
    }
}

@Service
public class ProductSearchService {
    private final ProductRepository repository;
    public ProductSearchService(ProductRepository repository) { this.repository = repository; }

    @Transactional(readOnly = true)
    public Page<Product> search(SearchRequest r, Pageable pageable) {
        Specification<Product> spec = Specification.allOf(
                ProductSpecs.nameContains(r.name()), ProductSpecs.inCategory(r.categories()),
                ProductSpecs.priceBetween(r.minPrice(), r.maxPrice()), ProductSpecs.hasTag(r.tag()));
        return repository.findAll(spec, pageable);
    }
}

A specification that returns null is ignored, so only filters the user filled become SQL conditions. Combine with and(), or(), not(), allOf(), anyOf(). Specification.where() is the older entry point.

Query by Example

Product probe = new Product();
probe.setCategory("books");
probe.setName("java");

ExampleMatcher matcher = ExampleMatcher.matching()
        .withIgnoreCase()
        .withStringMatcher(ExampleMatcher.StringMatcher.CONTAINING)      // name like %java%
        .withIgnorePaths("price", "createdAt")
        .withMatcher("category", ExampleMatcher.GenericPropertyMatchers.exact());

List<Product> result = repository.findAll(Example.of(probe, matcher));
// Limits: only AND, no > or <, no nested collections. Null probe fields are ignored. Good for simple search forms.

Querydsl (optional)

public interface ProductRepository extends JpaRepository<Product, Long>, QuerydslPredicateExecutor<Product> { }

QProduct p = QProduct.product;
BooleanBuilder where = new BooleanBuilder();
if (name != null) where.and(p.name.containsIgnoreCase(name));
if (min != null) where.and(p.price.goe(min));
Page<Product> page = repository.findAll(where, pageable);
// Web binding: @QuerydslPredicate Predicate predicate builds conditions from request parameters ?name=pen&price=10

Criteria API directly in a custom repository

public List<CategoryStat> stats(BigDecimal minAvg) {
    CriteriaBuilder cb = em.getCriteriaBuilder();
    CriteriaQuery<CategoryStat> q = cb.createQuery(CategoryStat.class);
    Root<Product> p = q.from(Product.class);
    q.select(cb.construct(CategoryStat.class, p.get(Product_.category), cb.count(p), cb.avg(p.get(Product_.price))))
     .groupBy(p.get(Product_.category))
     .having(cb.ge(cb.avg(p.get(Product_.price)), minAvg))
     .orderBy(cb.asc(p.get(Product_.category)));
    return em.createQuery(q).getResultList();
}
  • Write one Specification per filter, name them clearly and unit test them with @DataJpaTest.
  • Sort and page as usual: findAll(spec, pageable). The count query is derived from the same specification.
  • Watch the SQL of specifications with joins to collections: use distinct and prefer EXISTS subqueries for large data.

Common mistake: Joining a collection in a specification with paging and forgetting distinct. Rows multiply per child, pages contain duplicates and totals are wrong. Use query.distinct(true) or an EXISTS subquery.

Interview questions

Specification or @Query with optional parameters?

Do not write JPQL like (:name is null or p.name = :name) with many optionals: it defeats indexes and plans. A specification adds only the conditions that are present.

Why is my Specification count query failing with a fetch join?

The count query has no entity result, so root.fetch() is invalid there. Add the fetch only when the query result type is not Long.

Is Query by Example enough?

For simple equality or like filters yes. For ranges, ors, joins or subqueries use Specifications or Querydsl.
