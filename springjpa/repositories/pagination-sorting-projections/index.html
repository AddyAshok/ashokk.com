Pagination, Sorting and Projections

Loading everything is the fastest way to crash a service. Pagination, typed sorting and projections reduce data at the source. This page explains offset paging costs, keyset paging (Window), all projection types and when each is correct.

Pageable, Page and Slice

Pageable pageable = PageRequest.of(0, 20, Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("name")));
Page<Product> page = repository.findByCategory("books", pageable);

page.getContent();          // the 20 items
page.getTotalElements();    // from the COUNT query
page.getTotalPages();
page.hasNext();

Slice<Product> slice = repository.findSliceByCategory("books", pageable);   // no count query: fetches 21 rows to know if a next page exists
// Controller: public Page<ProductDto> list(@PageableDefault(size = 20, sort = "id") Pageable p)   ?page=0&size=20&sort=price,desc
TypeSQLCost
Pageselect ... limit ? offset ? + select count(*) ...Count query can be slow on big tables (full scan or big index scan)
Sliceselect ... limit size+1 offset ?No count
Window (keyset)select ... where (key) > (last key) order by key limit ?Constant time for any depth
List + Limit (Top N)select ... limit NCheapest, no paging

Offset paging gets slower with depth

select * from orders order by id limit 20 offset 1000000
   The database must READ and SKIP 1,000,000 rows to return 20.   page 50000 is 50000 times more work than page 0.
   Also unstable: inserts between requests make items appear twice or be skipped.
Keyset (seek) pagination:  select * from orders where id > :lastId order by id limit 20     uses the index: same speed on every page.

Keyset pagination with Window (Spring Data 3.1+)

public interface OrderRepository extends JpaRepository<OrderEntity, Long> {
    Window<OrderEntity> findFirst20ByStatusOrderByCreatedAtAscIdAsc(OrderStatus status, ScrollPosition position);
}

Window<OrderEntity> first = repository.findFirst20ByStatusOrderByCreatedAtAscIdAsc(OrderStatus.PAID, ScrollPosition.keyset());
while (true) {
    process(first.getContent());
    if (!first.hasNext()) break;
    first = repository.findFirst20ByStatusOrderByCreatedAtAscIdAsc(OrderStatus.PAID, first.positionAt(first.size() - 1));   // resume after the last row
}
// The sort MUST contain a unique tie-breaker (id). The API returns an opaque cursor to the client instead of page numbers.

Pageable safety

@Transactional(readOnly = true)
public Page<ProductDto> list(Pageable requested) {
    int size = Math.min(requested.getPageSize(), 100);                                    // never trust the client size
    Sort safeSort = requested.getSort().stream()
            .filter(o -> Set.of("name", "price", "createdAt").contains(o.getProperty()))  // allow-list of sortable fields
            .collect(Collectors.collectingAndThen(Collectors.toList(), Sort::by));
    Pageable safe = PageRequest.of(requested.getPageNumber(), size, safeSort.isEmpty() ? Sort.by("id") : safeSort);
    return repository.findAll(safe).map(ProductDto::from);
}

Fetch joins and paging: a trap

// join fetch on a COLLECTION with paging: Hibernate cannot limit rows in SQL (a parent repeats per child)
@Query("select o from OrderEntity o join fetch o.lines")
Page<OrderEntity> bad(Pageable p);
// WARN HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory   ==> loads EVERYTHING, then pages in Java

// Correct: page the parents, then load the collections for those ids
Page<Long> ids = repository.findIds(pageable);                                   // select o.id from OrderEntity o
List<OrderEntity> orders = repository.findWithLinesByIdIn(ids.getContent());     // join fetch where o.id in :ids
// or rely on hibernate.default_batch_fetch_size and page the plain entities

Projections: return only what is needed

KindExampleLoads
Interface, closedinterface NameView { String getName(); BigDecimal getPrice(); }Only the selected columns (query is optimized)
Interface, open (@Value SpEL)@Value("#{target.name + ' ' + target.sku}")The WHOLE entity, then computes. No SQL savings
Class / record DTOrecord ProductView(String name, BigDecimal price)Only constructor columns
Dynamic<T> List<T> findByCategory(String c, Class<T> type)Caller chooses the shape
Tuple@Query("select p.name as name, p.price as price from Product p") List<Tuple>Selected columns
public interface ProductRepository extends JpaRepository<Product, Long> {

    interface NameAndPrice { String getName(); BigDecimal getPrice(); }             // closed projection
    List<NameAndPrice> findByCategory(String category);                             // select p.name, p.price from products p where category = ?

    record ProductView(String name, BigDecimal price) { }
    List<ProductView> findViewByStatus(ProductStatus status);                       // DTO projection with a record

    <T> List<T> findByCategory(String category, Class<T> type);                     // dynamic: findByCategory("b", NameAndPrice.class) or Product.class

    interface CustomerOrders { String getName(); List<OrderInfo> getOrders(); interface OrderInfo { Long getId(); BigDecimal getTotal(); } }
    // nested interface projections of collections load the entity graph: check the SQL
}
  • Projections are the biggest easy performance win for list screens and APIs: fewer columns, no managed entities, no dirty checking.
  • A projected result is NOT managed: changes are not written back.
  • Interface projections of entities with relations may load the entities anyway. Use the DTO form for guaranteed selected columns.

Common mistake: Using join fetch on a collection together with Pageable. Hibernate then applies the paging in memory after loading all rows (a warning is logged), which can take down the application on big data. Page the parent ids first, or use batch fetching.

Interview questions

Why is deep offset pagination slow?

The database must scan and discard all skipped rows for every request. Keyset pagination uses an indexed condition on the last seen key and stays fast at any depth.

Page or Slice for an infinite scroll?

Slice (or Window). It avoids the count query and only tells whether more data exists.

Do projections make queries faster?

Closed interface and DTO projections select only the needed columns and skip entity management, so they usually reduce time, memory and network. Open projections still load the whole entity.
