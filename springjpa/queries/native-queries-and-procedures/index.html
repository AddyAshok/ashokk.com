Native SQL, Result Mapping and Stored Procedures

JPQL cannot express everything: window functions, database specific features, recursive queries, bulk moves. JPA lets you run native SQL and map the result, and call stored procedures. This page shows all mapping options and the risks.

Native query returning entities or values

// entity result: SELECT must return ALL columns of the entity
List<Product> products = em.createNativeQuery("select * from products where category = :c limit 10", Product.class)
        .setParameter("c", "books").getResultList();

// scalar result: Object[] per row (or Tuple)
List<Object[]> rows = em.createNativeQuery("select category, count(*) from products group by category").getResultList();

// Hibernate 6: direct DTO mapping with Tuple and aliases
List<Tuple> tuples = em.createNativeQuery("select category as category, count(*) as cnt from products group by category", Tuple.class).getResultList();
tuples.forEach(t -> System.out.println(t.get("category", String.class) + " " + t.get("cnt", Long.class)));

Native queries in repositories

public interface ProductRepository extends JpaRepository<Product, Long> {

    @Query(value = "select * from products p where p.tsv @@ plainto_tsquery(:q)", nativeQuery = true)          // PostgreSQL full text search
    List<Product> fullText(@Param("q") String q);

    @Query(value = "select p.category as category, p.name as name, p.price as price, "
                 + "rank() over (partition by p.category order by p.price desc) as rank "
                 + "from products p", nativeQuery = true)                                                        // window function
    List<RankedProduct> ranked();
    interface RankedProduct { String getCategory(); String getName(); BigDecimal getPrice(); Integer getRank(); }

    @Modifying
    @Transactional
    @Query(value = "insert into product_archive select * from products where status = 'ARCHIVED'", nativeQuery = true)
    int archive();
}

Recursive query (tree data)

@Query(value = "with recursive tree as ("
             + " select id, name, parent_id, 0 as depth from category where id = :root"
             + " union all"
             + " select c.id, c.name, c.parent_id, t.depth + 1 from category c join tree t on c.parent_id = t.id) "
             + "select id as id, name as name, depth as depth from tree order by depth, name", nativeQuery = true)
List<CategoryNode> subtree(@Param("root") Long root);

Native query cautions

  • Native queries are not portable across databases.
  • A native SELECT does not know about changes still pending in the persistence context. Hibernate flushes only the tables it knows: use query.addSynchronizedEntityClass(...), or call em.flush() before the query.
  • Entities returned by native queries are managed like any other. Use projections or Tuple for read-only data.
  • Sorting and paging: Spring Data cannot add Sort to a native query. Write order by yourself and give a countQuery for Page results.
  • Always use bound parameters, never string concatenation (SQL injection).

@SqlResultSetMapping (JPA standard)

@SqlResultSetMapping(name = "CategoryStatMapping",
    classes = @ConstructorResult(targetClass = CategoryStat.class,
        columns = { @ColumnResult(name = "category", type = String.class), @ColumnResult(name = "cnt", type = Long.class) }))
@NamedNativeQuery(name = "Product.categoryStats",
    query = "select category, count(*) as cnt from products group by category",
    resultSetMapping = "CategoryStatMapping")
@Entity public class Product { }

List<CategoryStat> stats = em.createNamedQuery("Product.categoryStats", CategoryStat.class).getResultList();

Stored procedures and functions

// Repository style
public interface OrderRepository extends JpaRepository<OrderEntity, Long> {
    @Procedure(procedureName = "calculate_tax")                 // CALL calculate_tax(?)  with one OUT parameter as return value
    BigDecimal calculateTax(@Param("order_id") Long orderId);
}

// Named procedure with IN and OUT parameters
@NamedStoredProcedureQuery(name = "OrderEntity.close", procedureName = "close_order",
    parameters = { @StoredProcedureParameter(mode = ParameterMode.IN, name = "p_id", type = Long.class),
                   @StoredProcedureParameter(mode = ParameterMode.OUT, name = "p_status", type = String.class) })
@Entity public class OrderEntity { }

StoredProcedureQuery q = em.createNamedStoredProcedureQuery("OrderEntity.close");
q.setParameter("p_id", 42L);
q.execute();
String status = (String) q.getOutputParameterValue("p_status");
// PostgreSQL functions returning a table are usually easier with a native SELECT: select * from my_function(:p)

Mixing JPA and JdbcTemplate in one transaction

@Service
public class MixedService {
    private final ProductRepository products;          // JPA
    private final JdbcTemplate jdbc;                   // plain SQL

    @Transactional                                     // JpaTransactionManager exposes the SAME JDBC connection to JdbcTemplate
    public void archive() {
        products.flush();                              // make pending JPA changes visible to the JDBC statement
        jdbc.update("insert into audit_log(action) values ('archive')");
        // both use the same connection and the same transaction (JpaDialect supports it)
    }
}

Common mistake: Running a native query right after changing entities in the same transaction and expecting to see the changes. Hibernate may not flush pending inserts before a native query. Call flush() first (or synchronize the entity classes).

Interview questions

Can I paginate a native query with Pageable?

Yes, but you must provide a countQuery for Page results and write the ORDER BY yourself, because Spring Data cannot rewrite native SQL safely.

Do JPA and JdbcTemplate share a transaction?

Yes with JpaTransactionManager. It binds the JDBC connection to the thread, and JdbcTemplate uses it. Flush the persistence context first if the JDBC code must see the entity changes.

When should I choose native SQL over JPQL?

For database specific features (window functions, full-text search, recursive queries, bulk moves) and reports. Keep the rest in JPQL for portability and type safety.
