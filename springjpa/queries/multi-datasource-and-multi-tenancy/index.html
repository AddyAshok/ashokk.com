Multiple Databases, Read Replicas and Multi-Tenancy

Real systems have more than one database: separate schemas for reporting, read replicas for scale, or one database per customer. This page shows how to configure several EntityManagerFactories, route reads to replicas, and the three multi-tenancy models.

Two databases with two persistence units

Package layout (each unit has its own entities and repositories):
com.example.orders.domain, com.example.orders.repo     ─► DataSource ordersDs ─► EntityManagerFactory ordersEmf ─► TransactionManager ordersTx
com.example.reports.domain, com.example.reports.repo   ─► DataSource reportsDs ─► EntityManagerFactory reportsEmf ─► TransactionManager reportsTx
@Transactional("ordersTx") picks the manager. A transaction NEVER spans both databases (no XA by default).
@Configuration
@EnableJpaRepositories(basePackages = "com.example.orders.repo", entityManagerFactoryRef = "ordersEmf", transactionManagerRef = "ordersTx")
public class OrdersJpaConfig {

    @Bean @Primary @ConfigurationProperties("app.datasource.orders")
    DataSourceProperties ordersProps() { return new DataSourceProperties(); }

    @Bean @Primary
    DataSource ordersDs(@Qualifier("ordersProps") DataSourceProperties p) { return p.initializeDataSourceBuilder().type(HikariDataSource.class).build(); }

    @Bean @Primary
    LocalContainerEntityManagerFactoryBean ordersEmf(EntityManagerFactoryBuilder builder, @Qualifier("ordersDs") DataSource ds) {
        return builder.dataSource(ds).packages("com.example.orders.domain").persistenceUnit("orders")
                .properties(Map.of("hibernate.hbm2ddl.auto", "validate")).build();
    }

    @Bean @Primary
    PlatformTransactionManager ordersTx(@Qualifier("ordersEmf") EntityManagerFactory emf) { return new JpaTransactionManager(emf); }
}
// Repeat for reports with other names (without @Primary) and other packages.

Flyway or Liquibase needs one configuration per datasource too (a FlywayMigrationInitializer bean per unit, or run migrations from separate modules).

Read replicas: route by transaction type

public class ReplicaRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly() ? "replica" : "primary";
    }
}

@Configuration
class RoutingConfig {
    @Bean
    DataSource dataSource(@Qualifier("primaryDs") DataSource primary, @Qualifier("replicaDs") DataSource replica) {
        ReplicaRoutingDataSource routing = new ReplicaRoutingDataSource();
        routing.setTargetDataSources(Map.of("primary", primary, "replica", replica));
        routing.setDefaultTargetDataSource(primary);
        return new LazyConnectionDataSourceProxy(routing);          // REQUIRED: delay getting the connection until the first SQL,
    }                                                               // after Spring has set the read-only flag of the transaction
}

@Transactional(readOnly = true)     // goes to the replica
public List<ProductView> list() { return repository.findViews(); }
@Transactional                      // goes to the primary
public void update() { }
  • Replicas are eventually consistent: a read right after a write may not see it (replication lag). Keep read-your-own-write flows on the primary.
  • Without LazyConnectionDataSourceProxy Spring acquires the connection before the readOnly flag is known and everything goes to the same database.
  • Size the pools separately and monitor the replication lag.

Multi-tenancy models

ModelIsolationCostHow in Hibernate/Spring
Database per tenantStrongestHighest: many pools and migrationsMultiTenantConnectionProvider + CurrentTenantIdentifierResolver, one DataSource per tenant
Schema per tenantStrongMedium: migrations per schemaSame providers, set search_path or schema per connection
Discriminator column (shared tables)Logical only: a bug leaks dataLowest@TenantId (Hibernate 6) or @Filter
// Schema per tenant (PostgreSQL)
@Component
public class SchemaMultiTenantConnectionProvider implements MultiTenantConnectionProvider<String> {
    private final DataSource dataSource;
    public SchemaMultiTenantConnectionProvider(DataSource dataSource) { this.dataSource = dataSource; }

    @Override public Connection getAnyConnection() throws SQLException { return dataSource.getConnection(); }
    @Override public void releaseAnyConnection(Connection c) throws SQLException { c.close(); }

    @Override
    public Connection getConnection(String tenantId) throws SQLException {
        Connection c = dataSource.getConnection();
        try (Statement st = c.createStatement()) { st.execute("set search_path to \"" + sanitize(tenantId) + "\""); }
        return c;
    }
    @Override
    public void releaseConnection(String tenantId, Connection c) throws SQLException {
        try (Statement st = c.createStatement()) { st.execute("set search_path to public"); }
        c.close();
    }
    @Override public boolean supportsAggressiveRelease() { return false; }
    @Override public boolean isUnwrappableAs(Class<?> type) { return false; }
    @Override public <T> T unwrap(Class<T> type) { return null; }

    private static String sanitize(String t) {
        if (!t.matches("[a-z0-9_]{1,30}")) throw new IllegalArgumentException("bad tenant");      // never build SQL from unchecked input
        return t;
    }
}
// register: spring.jpa.properties.hibernate.multi_tenant_connection_provider = ...   and tenant_identifier_resolver = ...
// The tenant id is set per request (filter reading a header or JWT claim into a TenantContext ThreadLocal, cleared in finally).
  • Where the tenant id comes from must be trusted: take it from the authenticated token, not from a header the client controls.
  • Cache keys, file paths and background jobs must include the tenant too, or data leaks across tenants.
  • Test with two tenants that one can never read the other's rows.

Common mistake: Taking the tenant id from a client controlled header without verifying it against the authenticated user. Any user could read another tenant's data by changing the header. Derive the tenant from the authenticated identity.

Interview questions

Can one @Transactional cover two databases?

Not with plain JPA transaction managers: each manager handles one database. Use eventual consistency (outbox, events), or XA/JTA only when unavoidable.

Why does my read replica routing not work?

Usually LazyConnectionDataSourceProxy is missing, so the connection is taken before the read-only flag is set, or readOnly is not set on the transaction.

Which multi-tenancy model should I choose?

Shared tables with @TenantId for many small tenants, schema per tenant for medium isolation needs, database per tenant for the strongest isolation and big tenants.
