Primary Keys and ID Generation Strategies

How an entity gets its id affects batching, memory, concurrency and even whether save() runs an extra SELECT. This page explains every strategy with its internal behavior, composite keys, and the isNew trap for assigned ids.

Strategies compared

SEQUENCE with the pooled optimizer

@Entity
public class Invoice {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "invoice_seq")
    @SequenceGenerator(name = "invoice_seq", sequenceName = "invoice_seq", allocationSize = 50)
    private Long id;
}
// The database sequence must be created with INCREMENT BY 50 (Flyway):  CREATE SEQUENCE invoice_seq START 1 INCREMENT 50;
allocationSize = 50, pooled optimizer:
 first persist:   SELECT nextval('invoice_seq')  ─► 51    Hibernate now owns the ids 1..50 in memory (no more database calls)
 next 49 persists: ids 2, 3, 4 ... 50 are handed out from memory, ZERO extra queries
 the 51st persist: SELECT nextval  ─► 101  ─► ids 51..100
Result: 1 sequence call for 50 inserts, and all INSERTs can be batched.
If the database increment does not match allocationSize (sequence +1, allocationSize 50) Hibernate warns or produces duplicate ids: keep them equal.

IDENTITY and its price

@Id @GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
// persist(order): Hibernate MUST run INSERT right now to read the generated id.
// Inserting 1000 entities = 1000 separate INSERT round trips, no batching, even with hibernate.jdbc.batch_size set.
// Fine for low volume. For bulk inserts choose SEQUENCE.

UUID keys

@Id
@GeneratedValue(strategy = GenerationType.UUID)                  // Jakarta Persistence 3.1, Hibernate 6.2+
private UUID id;

// Better index locality with time-ordered UUIDs (version 7, or Hibernate's @UuidGenerator(style = TIME))
@Id
@GeneratedValue
@UuidGenerator(style = UuidGenerator.Style.TIME)
private UUID id;
UUIDProsCons
Random (v4)No coordination, safe to expose, ids known before insert16 bytes, random inserts fragment the primary key B-tree index, slower inserts on big tables
Time-ordered (v1 style, v7)Same benefits, sequential-like insertsReveals creation time
Long sequenceSmall, fast, orderedGuessable (add authorization checks), needs the database for allocation

Composite keys

// Option 1: @EmbeddedId (recommended)
@Embeddable
public class OrderLineId implements Serializable {
    private Long orderId;
    private Integer lineNo;
    protected OrderLineId() { }
    public OrderLineId(Long orderId, Integer lineNo) { this.orderId = orderId; this.lineNo = lineNo; }
    @Override public boolean equals(Object o) { return o instanceof OrderLineId x && Objects.equals(orderId, x.orderId) && Objects.equals(lineNo, x.lineNo); }
    @Override public int hashCode() { return Objects.hash(orderId, lineNo); }
}

@Entity
public class OrderLine {
    @EmbeddedId private OrderLineId id;
    private int quantity;
}
public interface OrderLineRepository extends JpaRepository<OrderLine, OrderLineId> { List<OrderLine> findByIdOrderId(Long orderId); }

// Option 2: @IdClass (fields stay in the entity)
@Entity @IdClass(OrderLineId.class)
public class OrderLine2 { @Id private Long orderId; @Id private Integer lineNo; }

The isNew trap with assigned ids

SimpleJpaRepository.save() decides between persist and merge with isNew(). For an entity with a generated id, id == null means new. For an assigned id (you always set it), id is never null, so Spring Data thinks the entity is NOT new and calls merge(). merge() first runs a SELECT to see whether the row exists, then INSERT: two statements and a copy of the object.

@Entity
public class Country implements Persistable<String> {

    @Id private String code;                        // assigned natural key
    private String name;

    @Transient private boolean isNew = true;        // not stored

    protected Country() { }
    public Country(String code, String name) { this.code = code; this.name = name; }

    @Override public String getId() { return code; }
    @Override public boolean isNew() { return isNew; }

    @PostPersist @PostLoad void markNotNew() { this.isNew = false; }       // after save or load it is an existing row
}
// Alternative: add @Version Long version. A null version means new, and save() calls persist without the extra SELECT.

Natural vs surrogate keys

  • Surrogate key (generated number or UUID): stable, small, no business meaning. Recommended as primary key.
  • Natural key (email, ISBN, SKU): often changes or is not unique in practice. Keep it as a UNIQUE column, and in Hibernate mark it with @NaturalId for fast lookups.
  • Never expose database ids as the only protection of a resource: always check authorization.

Common mistake: Using GenerationType.IDENTITY for tables that receive bulk inserts, then wondering why hibernate.jdbc.batch_size has no effect. Use SEQUENCE with allocationSize equal to the sequence increment.

Interview questions

Why is batch insert not working with IDENTITY?

Hibernate needs the generated id right after each INSERT, so it executes every INSERT immediately and cannot group them. SEQUENCE ids are known in advance, so INSERTs are grouped at flush.

Why does save() run a SELECT before INSERT?

The entity has an assigned id and no @Version, so Spring Data treats it as existing and uses merge(), which loads the row first. Implement Persistable or add @Version.

Which UUID version should I use?

Prefer time-ordered UUIDs (v7 or Hibernate TIME style) for large tables, because random v4 keys fragment the index.
