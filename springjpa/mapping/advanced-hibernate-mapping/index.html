Advanced Hibernate Mapping: Formula, NaturalId, Filters, Immutable, TenantId and more

Hibernate offers many mapping features beyond JPA. They solve real problems: computed fields, business keys, soft delete, read-only views, multi-tenancy and batch loading. Use them on purpose.

Overview

FeatureAnnotationUse for
Computed column@Formula("...sql...")Read only value computed by SQL
Business key lookup@NaturalIdFast lookup by email or sku with a cached mapping to id
Soft delete@SQLDelete + @SQLRestrictionMark as deleted instead of removing rows
Filter by parameter@FilterDef + @FilterMulti-tenancy, active data only, switchable per session
Discriminator tenant@TenantId (Hibernate 6.0+)Row level multi-tenancy
Read only entity@ImmutableReference data, views. No dirty checking, no updates
Entity on a query@SubselectMap a SQL query as a read only entity
Update only changed columns@DynamicUpdateWide tables, avoid overwriting concurrent changes
Insert only set columns@DynamicInsertLet database defaults apply
Batch load associations@BatchSize(size = 25)Defend against N+1
Fetch mode@Fetch(FetchMode.SUBSELECT)Load all collections of the loaded parents in one query
Database generated value@Generated / @CurrentTimestampValues computed by the database
JSON attribute@JdbcTypeCode(SqlTypes.JSON)Store objects as json or jsonb

@Formula

@Entity
public class Customer {
    @Id @GeneratedValue private Long id;

    @Formula("(select count(*) from orders o where o.customer_id = id)")
    private Long orderCount;                                     // computed when the customer is loaded (extra subquery each time)

    @Formula("concat(first_name, ' ', last_name)")
    private String fullName;
}

@NaturalId: fast business key lookup

@Entity
public class User {
    @Id @GeneratedValue private Long id;
    @NaturalId @Column(nullable = false, unique = true) private String email;      // immutable by default
}

Optional<User> user = em.unwrap(Session.class).bySimpleNaturalId(User.class).loadOptional("ram@example.com");
// Uses a cache from natural id to primary key in the persistence context: repeated lookups need no SQL

Soft delete

@Entity
@SQLDelete(sql = "update customer set deleted = true, deleted_at = now() where id = ? and version = ?")
@SQLRestriction("deleted = false")                                // Hibernate 6.3+, older: @Where(clause = "deleted = false")
public class Customer {
    @Id @GeneratedValue private Long id;
    @Version private Long version;
    private boolean deleted;
    private Instant deletedAt;
}
// repository.delete(customer)  ─► UPDATE. All selects add "and deleted = false".
// Native queries and unique constraints ignore the restriction: use a partial unique index (where deleted = false).

Filters: switchable conditions

@Entity
@FilterDef(name = "tenantFilter", parameters = @ParamDef(name = "tenantId", type = Long.class), defaultCondition = "tenant_id = :tenantId")
@Filter(name = "tenantFilter")
public class Invoice {
    @Id @GeneratedValue private Long id;
    @Column(name = "tenant_id") private Long tenantId;
}

// enable per transaction (AOP or a transaction callback)
@Transactional
public List<Invoice> invoicesFor(long tenantId) {
    em.unwrap(Session.class).enableFilter("tenantFilter").setParameter("tenantId", tenantId);
    return em.createQuery("select i from Invoice i", Invoice.class).getResultList();
}
// Filters apply to queries, NOT to em.find(id) by primary key.

@TenantId: row level tenant column

@Entity
public class Order {
    @Id @GeneratedValue private Long id;
    @TenantId private String tenantId;                 // set automatically on insert, added to every query
}

@Component
public class TenantResolver implements CurrentTenantIdentifierResolver<String> {
    @Override public String resolveCurrentTenantIdentifier() { return TenantContext.current(); }
    @Override public boolean validateExistingCurrentSessions() { return true; }
}
// register: spring.jpa.properties.hibernate.tenant_identifier_resolver=com.example.TenantResolver

Read only data: @Immutable and @Subselect

@Entity @Immutable
@Table(name = "country")
public class Country { @Id private String code; private String name; }         // never updated, skipped by dirty checking

@Entity @Immutable
@Subselect("select c.id as id, c.name as name, count(o.id) as orders from customer c left join orders o on o.customer_id = c.id group by c.id, c.name")
@Synchronize({ "customer", "orders" })                                          // flush pending changes of these tables before querying this entity
public class CustomerSummary { @Id private Long id; private String name; private long orders; }

Enable batch loading for one association

@OneToMany(mappedBy = "customer")
@BatchSize(size = 25)                       // load orders of up to 25 customers with one "where customer_id in (?, ?, ... )"
private List<OrderEntity> orders = new ArrayList<>();

@Entity @BatchSize(size = 50) public class Country { }      // proxies of Country are initialized 50 at a time

Bytecode enhancement (optional)

With the hibernate-enhance-maven-plugin you can enable lazy loading of basic attributes (@Basic(fetch = LAZY) for a big description column), bytecode based dirty tracking (no snapshot comparison) and lazy one-to-one on the inverse side. It changes the build, so use it only when profiling shows a need.

Common mistake: Using @Formula with an expensive subquery on a popular entity. The subquery runs every time the entity is loaded, even in lists where the value is not needed. Compute it in a projection query for the screens that need it.

Interview questions

What is the difference between @Where and @Filter?

@Where (@SQLRestriction) is always applied and cannot be turned off. @Filter can be enabled or disabled per session and takes parameters, so it fits multi-tenancy.

Does soft delete affect em.find()?

@SQLRestriction is added to entity loading, including find by id in Hibernate. Native queries ignore it.

When would I choose @DynamicUpdate?

For very wide tables, or when different transactions change different columns of the same row and you want to avoid overwriting untouched columns. It costs a new SQL string per combination of changed columns.
