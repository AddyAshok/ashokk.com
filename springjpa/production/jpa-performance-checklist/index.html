JPA Performance Checklist and Tuning Method

A practical order of work for a slow JPA application: measure, find the biggest cost, fix it, measure again. The checklist covers the mistakes that cause most real problems.

Method

1. Measure     SQL count and time per request (statistics, datasource-proxy, tracing), slow query log of the database
2. Find        the ONE most expensive thing (usually: too many queries, one slow query, huge result, or waiting for connections)
3. Fix         in this order: queries and indexes, fetching, batching, pool/transactions, caching, only then hardware
4. Verify      the same measurement again. Add a test that guards the fix (query count assertion)

Checklist by area

AreaCheckFix
Query countMore than a handful of statements per request?Fetch joins, entity graphs, batch fetch size, projections
Result sizeUnbounded findAll(), big collections, many columns?Pagination with a size cap, projections, Slice/Window
Slow queryFull table scan, sort of a big set, function on indexed column?Index, rewrite predicate, EXPLAIN ANALYZE, keyset paging
WritesOne statement per row, IDENTITY, huge flush?SEQUENCE + batch_size + order_inserts, bulk JPQL/JDBC
Persistence contextMemory grows in loops and slow flushes?flush + clear in chunks, readOnly transactions, StatelessSession
TransactionsLong transactions, remote calls inside?Keep them short, no HTTP calls, no user interaction inside
ConnectionsThreads waiting for the pool? open-in-view true?open-in-view=false, shorter transactions, pool sizing
MappingEAGER associations, bags, @Formula subqueries, big @Lob on hot entities?LAZY, Set, separate entity/projection for big columns
CachingRepeated identical reads?Spring Cache for hot paths. Second level cache only for read-mostly data
LocksWaits, deadlocks, optimistic failures?Atomic SQL, consistent lock order, retry

Ten rules that fix most problems

  • 1. All associations LAZY, fetch explicitly per use case.
  • 2. open-in-view=false and map to DTOs in the service.
  • 3. Read paths return projections, not entities.
  • 4. Never findAll() on a growing table. Always paginate and cap the page size.
  • 5. hibernate.default_batch_fetch_size = 16 to 100 as a safety net.
  • 6. Use SEQUENCE ids with allocationSize equal to the sequence increment, enable JDBC batching.
  • 7. Index every foreign key and every column used in WHERE and ORDER BY.
  • 8. Keep transactions short: no remote calls, no waiting.
  • 9. Use readOnly = true for read use cases.
  • 10. Count queries in tests for the important use cases.

Indexes: what to check

-- foreign keys are NOT indexed automatically in PostgreSQL
create index idx_orders_customer_id on orders (customer_id);
create index idx_order_line_order_id on order_line (order_id);
-- composite index: order matters (equality columns first, then range/sort)
create index idx_orders_status_created on orders (status, created_at desc);
-- see the plan
explain (analyze, buffers) select * from orders where status = 'PAID' order by created_at desc limit 20;
-- partial index for soft delete or active rows
create unique index uk_users_email_active on users (email) where deleted = false;

Typical before and after

// BEFORE: 1 + N + N queries, loads entities and collections only to count
@Transactional(readOnly = true)
public List<CustomerDto> list() {
    return customerRepository.findAll().stream()
            .map(c -> new CustomerDto(c.getName(), c.getOrders().size())).toList();
}

// AFTER: one query, only the needed columns, database does the counting
public interface CustomerRepository extends JpaRepository<Customer, Long> {
    @Query("select new com.example.CustomerDto(c.name, count(o)) from Customer c left join c.orders o group by c.id, c.name")
    List<CustomerDto> summaries();
}

Production monitoring

  • Metrics: hikaricp.connections.active/pending, hibernate statistics (query execution max time, entity fetch count), http server request percentiles.
  • Database: pg_stat_statements (top queries by total time), slow query log, lock waits.
  • Tracing: spans for JDBC calls (datasource-micrometer) show how many queries a request makes.
  • Alerts: connection wait time, queries per request, p99 latency of the main endpoints.

Common mistake: Optimizing with guesses (adding caches, raising pool size) before counting SQL statements. Most JPA performance problems are query count and missing indexes, which you see immediately with SQL logging and EXPLAIN.

Interview questions

What is the first thing to check for a slow JPA endpoint?

How many SQL statements it runs and how long each takes. N+1 queries and missing indexes explain most cases.

Does readOnly = true improve performance?

Yes: Hibernate skips dirty checking and flush for the session (FlushMode.MANUAL), and some drivers and databases optimize read-only connections.

Should I use the Hibernate second level cache to fix slow reads?

Only for read-mostly reference data after measuring. First fix queries, fetching and indexes.
