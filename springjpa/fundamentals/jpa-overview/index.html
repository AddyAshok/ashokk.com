JPA, Hibernate and Spring Data JPA: The Big Picture

Three names are mixed up in almost every project: JPA, Hibernate and Spring Data JPA. They are three different layers. Understanding what each layer does, and what happens between your repository call and the SQL that runs, is the base for every other topic in this course.

The problem: objects and tables do not match

Object world (Java)Relational world (SQL)Mismatch
Classes, inheritance, polymorphismTables, no inheritanceGranularity and inheritance mapping
Object references (order.customer)Foreign keys, joinsAssociation direction and identity
Object identity (==) and equals()Primary keySame row can be several Java objects
Collections (List<OrderLine>)Child table rowsLoading strategy (lazy or eager)
Navigation graph (a.b.c.d)Set based queriesN+1 queries when navigating
Types: Instant, enum, JSON objectColumn typesType conversion

An ORM (object-relational mapper) hides this gap: you work with objects, and the ORM generates SQL. The price is that you must understand how it works, otherwise it generates too many or wrong queries.

The three layers

┌────────────────────────────────────────────────────────────────────────────┐
│ Your code:  service ─► productRepository.findByName("Pen")                 │
├────────────────────────────────────────────────────────────────────────────┤
│ SPRING DATA JPA   generates repository implementations from interfaces     │
│   (JpaRepository, query methods, paging, specifications, auditing)         │
│   uses ─►  EntityManager                                                   │
├────────────────────────────────────────────────────────────────────────────┤
│ JPA (Jakarta Persistence)   the STANDARD API: annotations (@Entity),       │
│   EntityManager, JPQL, Criteria API, entity lifecycle                      │
│   only interfaces and rules, no code that talks to the database            │
├────────────────────────────────────────────────────────────────────────────┤
│ HIBERNATE ORM   the IMPLEMENTATION of JPA (the default in Spring Boot)     │
│   persistence context, dirty checking, SQL generation, caches, proxies     │
│   uses ─►  JDBC                                                            │
├────────────────────────────────────────────────────────────────────────────┤
│ JDBC + HikariCP connection pool  ──►  JDBC driver ──►  DATABASE            │
└────────────────────────────────────────────────────────────────────────────┘
LayerPackage / artifactWhat you write there
Spring Data JPAorg.springframework.data.jpa.repository.*Repository interfaces, @Query, Specifications, @EnableJpaAuditing
JPAjakarta.persistence.* (javax.persistence before Boot 3)@Entity, @Id, @OneToMany, EntityManager, JPQL
Hibernateorg.hibernate.*@BatchSize, @Formula, @NaturalId, @DynamicUpdate, statistics, caching

Rule: write against JPA annotations and Spring Data as much as possible, and use Hibernate specific features when JPA has no answer (batch fetching, natural ids, JSON columns).

What happens when you call repository.save(product)

service.create()   @Transactional
  └─ productRepository.save(p)                          Spring proxy of the repository interface
       └─ SimpleJpaRepository.save
            ├─ isNew(p)?   yes ─► entityManager.persist(p)        no ─► entityManager.merge(p)
            └─ Hibernate Session (the EntityManager):
                 1. entity becomes MANAGED, stored in the persistence context (first level cache)
                 2. INSERT is queued in the ActionQueue        (immediately for IDENTITY ids)
  ... end of the service method ─► transaction commit
       └─ flush: dirty checking, ActionQueue executed ─► JDBC PreparedStatement batch ─► INSERT INTO product ...
       └─ COMMIT on the database connection, connection returns to the pool

Strengths and costs of the approach

StrengthCost
Very little boilerplate, portable across databasesHidden SQL: you must watch what runs (show SQL, statistics)
Automatic change detection (dirty checking)Memory and CPU for large numbers of managed entities
Rich mapping (relations, inheritance)Wrong fetch settings cause N+1 and huge joins
Caching (first and second level)Stale data and invalidation complexity
Transactions and concurrency (@Version)You must understand flush, lazy loading and detached objects

When JPA is NOT the best tool

  • Reports and analytics with big joins and aggregations: use native SQL, jOOQ or JdbcTemplate.
  • Very high volume bulk inserts and updates: use JDBC batching, StatelessSession or COPY.
  • Simple, read-only lists: use DTO projections and skip entities.
  • A mix is normal: JPA for the domain model and writes, SQL for reports.

Common mistake: Treating JPA as magic and never looking at the SQL it produces. Turn SQL logging on from day one and check the number of statements of every use case.

Interview questions

What is the difference between JPA and Hibernate?

JPA is the specification (interfaces and annotations). Hibernate is the most used implementation. Spring Boot uses Hibernate by default, but JPA code could run on EclipseLink.

What does Spring Data JPA add on top of JPA?

It generates repository implementations, query methods from method names, paging and sorting, specifications, auditing and transaction defaults, so you write far less DAO code.

Is JPA slow?

Not by itself. Problems come from misuse: N+1 queries, loading entities where projections would do, long transactions and huge persistence contexts.
