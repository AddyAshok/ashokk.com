Locking and Concurrency: Optimistic, Pessimistic, Isolation and Retries

When two users change the same row, someone must lose or wait. JPA gives you optimistic locking with a version column, pessimistic database locks, and lock modes. Choose the right one, and handle the failures correctly.

The problem: lost update

stock = 10.  Two requests each: read stock, subtract 1, write.
 T1 read 10                T2 read 10
 T1 write 9  COMMIT        T2 write 9  COMMIT      ◄── result 9, should be 8: one update is LOST
Locking, atomic SQL or a higher isolation level is required.

Optimistic locking with @Version

@Entity
public class Product {
    @Id @GeneratedValue private Long id;
    @Version private Long version;                 // Hibernate increments it on every update
    private int stock;
}
// update product set stock=?, version=4 where id=? and version=3     (the version in the WHERE clause)
// 0 rows updated ─► the row was changed by someone else ─► ObjectOptimisticLockingFailureException
T1: load (version 3)                        T2: load (version 3)
T1: stock 10 -> 9, flush: UPDATE ... WHERE version = 3  ─► 1 row, version now 4   COMMIT
                                                     T2: stock 10 -> 9, flush: UPDATE ... WHERE version = 3 ─► 0 rows
                                                     ─► OptimisticLockException ─► T2 rolls back ─► retry: reload (version 4), apply again
@Service
public class StockService {

    @Retryable(retryFor = ObjectOptimisticLockingFailureException.class, maxAttempts = 3, backoff = @Backoff(delay = 50, multiplier = 2))
    @Transactional
    public void reserve(Long productId, int quantity) {
        Product p = productRepository.findById(productId).orElseThrow();
        if (p.getStock() < quantity) throw new OutOfStockException(productId);
        p.setStock(p.getStock() - quantity);                    // version check happens at flush/commit
    }
}   // @Retryable (spring-retry, or Spring Framework 7 @Retryable): every attempt runs in a NEW transaction because the annotation is OUTSIDE @Transactional

@RestControllerAdvice
class ConflictHandler {
    @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
    ProblemDetail conflict() { return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "The data was changed by someone else. Reload and try again."); }
}

For REST APIs send the version as an ETag and require If-Match on PUT: the client updates only the version it saw. That turns optimistic locking into a contract with the client.

Atomic SQL: the best fix for counters

@Modifying
@Query("update Product p set p.stock = p.stock - :qty where p.id = :id and p.stock >= :qty")
int reserve(@Param("id") Long id, @Param("qty") int qty);       // returns 0 when there was not enough stock. No read, no lock held across statements

Pessimistic locking

public interface AccountRepository extends JpaRepository<Account, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)                      // select ... for update
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))     // wait max 3 s
    @Query("select a from Account a where a.id = :id")
    Optional<Account> lockById(@Param("id") Long id);
}

@Transactional
public void transfer(Long from, Long to, BigDecimal amount) {
    Long first = Math.min(from, to), second = Math.max(from, to);          // ALWAYS lock in the same order: avoids deadlocks
    Account a = accounts.lockById(first).orElseThrow();
    Account b = accounts.lockById(second).orElseThrow();
    // ... move the money. Locks are released at commit or rollback
}

Job queue with SKIP LOCKED

// Many workers take different jobs without blocking each other
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "-2"))      // -2 = SKIP LOCKED (Hibernate)
@Query("select j from Job j where j.status = 'NEW' order by j.createdAt")
List<Job> nextJobs(Pageable limit);            // PageRequest.of(0, 10)

Hibernate's first level cache already gives repeatable reads for entities loaded by id in one transaction. Isolation levels matter for queries and for concurrent writers. Prefer optimistic locking and atomic SQL over raising the isolation level.

Deadlocks

T1: lock row A ─► wants row B          T2: lock row B ─► wants row A          both wait forever ─► the database kills one (deadlock detected)
Rules: lock rows in a consistent order (by id), keep transactions short, do not call remote services while holding locks,
       catch CannotAcquireLockException / PessimisticLockingFailureException and retry the whole transaction.

Common mistake: Catching an optimistic lock exception inside the same @Transactional method and continuing. The persistence context is in an inconsistent state and the transaction is marked rollback-only. Let the exception leave the transaction and retry the whole unit of work from outside.

Interview questions

Optimistic or pessimistic locking?

Start with optimistic locking (@Version). Use pessimistic locks for hot rows with frequent conflicts (balances, stock) or queue processing with SKIP LOCKED. Use atomic UPDATE statements for simple counters.

Why must the retry be outside the transaction?

A failed transaction is rolled back and its persistence context is dead. A retry needs a new transaction and freshly loaded data.

Does @Version protect bulk updates?

No. A JPQL update statement does not touch the version unless you write it (set p.version = p.version + 1). Use versioned bulk update syntax: update versioned Product p set ... in HQL.
