Fetching Strategies, Lazy Loading, Proxies and the N+1 Problem

Loading data correctly is the most important performance skill in JPA. This page explains lazy and eager fetching, how proxies work, the exact sequence of the N+1 problem, and all the fixes with their trade-offs.

Fetch type defaults

AssociationDefaultRecommended
@ManyToOne, @OneToOneEAGERLAZY (always set it)
@OneToMany, @ManyToMany, @ElementCollectionLAZYLAZY
Basic attribute (@Basic)EAGER (no laziness without bytecode enhancement)Keep big columns in a separate entity or projection

FetchType is a HINT for how to load by default. You override it per query with fetch joins and entity graphs. Never fix a lazy problem by making the mapping EAGER: it loads the data in every use case, forever.

How lazy loading works: proxies and collection wrappers

order = orderRepository.findById(1L)        select o.* from orders o where id = 1
order.getCustomer()          returns a PROXY  (ByteBuddy subclass of Customer, only the id is known, NO SQL yet)
order.getCustomer().getId()  no SQL: the id is already in the proxy
order.getCustomer().getName()  ─► the proxy sees it is uninitialized ─► asks its Session ─► select c.* from customer c where id = ?  ─► fills the target
   Session closed at that moment?  ─► LazyInitializationException: could not initialize proxy - no Session

order.getLines()  returns a PersistentBag (wrapper). Iterating it triggers:  select l.* from order_line l where l.order_id = ?

The N+1 problem, step by step

@Transactional(readOnly = true)
public List<OrderDto> list() {
    List<OrderEntity> orders = orderRepository.findAll();                 // 1 query:   select * from orders          (100 rows)
    return orders.stream()
            .map(o -> new OrderDto(o.getId(), o.getCustomer().getName(),  // +100 queries: select * from customer where id = ?   (one per order)
                                   o.getLines().size()))                  // +100 queries: select * from order_line where order_id = ?
            .toList();                                                    // total 1 + 100 + 100 = 201 statements for one API call
}

With 100 rows you might not notice. With 10,000 rows it is 20,001 queries. Also each query is a network round trip, so latency grows linearly with the data size.

How to detect it

  • Turn on SQL logging in development and count the statements of every use case.
  • Use Hibernate statistics in tests: assert getPrepareStatementCount() is small and constant.
  • Tools: datasource-proxy or p6spy (query counter), Hypersistence Optimizer, Datasource Micrometer tracing.
  • Watch the metric hibernate.query.executions and the number of connections used per request.
// A test that fails when someone introduces N+1
@Test
void listOrdersUsesConstantQueries() {
    Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
    stats.setStatisticsEnabled(true);
    stats.clear();

    orderService.list();

    assertThat(stats.getPrepareStatementCount()).isLessThanOrEqualTo(2);
}

Fixes

FixHowResultCaution
1. JOIN FETCHselect o from OrderEntity o join fetch o.customerOne query with a joinDo not fetch two collections at once. Collection fetch + paging = in-memory paging
2. @EntityGraph@EntityGraph(attributePaths = {"customer"}) on the repository methodSame as join fetch, no JPQLSame limits
3. Batch fetchinghibernate.default_batch_fetch_size=50 or @BatchSize1 + N/50 queries using IN listsCheap to enable, works with paging
4. Subselect fetch@Fetch(FetchMode.SUBSELECT) on a collectionOne query for all collections of the loaded parentsRe-runs the original query as a subquery
5. DTO projectionselect new Dto(o.id, c.name, size(o.lines)) ... group byExactly the columns needed, no entitiesBest for read APIs
6. Two step loadingLoad parent ids with paging, then load associations for those idsCorrect paging with collectionsTwo queries
public interface OrderRepository extends JpaRepository<OrderEntity, Long> {

    @Query("select o from OrderEntity o join fetch o.customer")                       // ToOne: join fetch is safe, rows do not multiply
    List<OrderEntity> findAllWithCustomer();

    @EntityGraph(attributePaths = { "customer", "lines" })
    List<OrderEntity> findByStatus(OrderStatus status);

    @Query("select new com.example.OrderRow(o.id, c.name, count(l)) from OrderEntity o join o.customer c left join o.lines l group by o.id, c.name")
    List<OrderRow> summary();                                                          // no entities, one flat query

    @Query("select o.id from OrderEntity o where o.status = :s")
    Page<Long> findIds(@Param("s") OrderStatus s, Pageable p);                        // step 1 of two step loading
    @Query("select distinct o from OrderEntity o join fetch o.lines where o.id in :ids")
    List<OrderEntity> findWithLines(@Param("ids") List<Long> ids);                    // step 2
}

Entity graph types

@EntityGraph(attributePaths = "customer", type = EntityGraph.EntityGraphType.FETCH)   // listed attributes EAGER, all others LAZY
@EntityGraph(attributePaths = "customer", type = EntityGraph.EntityGraphType.LOAD)    // listed EAGER, others keep their mapping default

// Named graph on the entity
@Entity
@NamedEntityGraph(name = "Order.full", attributeNodes = { @NamedAttributeNode("customer"), @NamedAttributeNode(value = "lines", subgraph = "line") },
                  subgraphs = @NamedSubgraph(name = "line", attributeNodes = @NamedAttributeNode("product")))

LazyInitializationException: correct fixes

Wrong fixRight fix
Make the association EAGERLoad what the use case needs (fetch join, entity graph, projection) inside the service transaction
spring.jpa.open-in-view=trueKeep it false. Map to DTOs in the service
Hibernate.initialize() everywhereOnly as a last resort in a service. Prefer explicit fetching
enable_lazy_load_no_trans=true (Hibernate property)Never: opens a new session and connection per lazy access (an anti-pattern that hides N+1)

Cartesian product warning

select o from Order o join fetch o.lines join fetch o.payments      (two collections)
 order with 10 lines and 5 payments returns 10 x 5 = 50 rows for ONE order (with a Set; with Lists: MultipleBagFetchException)
Fix: fetch one collection per query, or use batch fetching. The persistence context merges the results into the same entity instances.

Common mistake: Making @ManyToOne or collections EAGER to silence LazyInitializationException. Every query then loads extra tables and creates N+1 problems everywhere. Keep everything LAZY and fetch explicitly per use case.

Interview questions

What is the N+1 problem?

One query loads N parent rows, and then one additional query per parent loads an association when it is accessed, giving N+1 statements. It is fixed with fetch joins, entity graphs, batch fetching or projections.

Why does a fetch join with Pageable cause a warning?

A join on a collection repeats each parent for every child, so LIMIT would cut in the middle of a parent. Hibernate loads all rows and pages in memory (HHH90003004).

Join fetch or batch fetching?

Join fetch for one or two ToOne or one collection when you always need it. Batch fetching as a general safety net, and it works together with paging.
