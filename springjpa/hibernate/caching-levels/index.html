Caching in JPA: First Level, Second Level and Query Cache

Hibernate has three caches with very different behavior. The first level cache is always on and defines how JPA works. The second level and query cache are optional performance tools that need careful design. Add your application cache (Spring Cache) on top only where it makes sense.

Overview

Request/transaction ─► EntityManager ─► 1. FIRST LEVEL cache (persistence context)   per EntityManager, always on
                                              miss ─► 2. SECOND LEVEL cache (region per entity)     per SessionFactory, shared, OPTIONAL
                                                         miss ─► 3. DATABASE
Query cache (optional): caches the LIST OF IDS of a query result. Entities themselves come from the second level cache.
Spring @Cacheable: caches whatever your method returns (DTOs, lists) outside of Hibernate.
CacheScopeDefaultShared between transactionsInvalidation
First levelOne EntityManager (transaction)Always onNoEnds with the transaction. clear() and detach()
Second levelSessionFactory (JVM), or distributedOffYesHibernate updates it on changes made through Hibernate (NOT on bulk SQL or other applications)
Query cacheSessionFactoryOffYesInvalidated when ANY table of the query changes (timestamps cache)
Spring @CacheableYour CacheManagerOffYesYou control it (evict, TTL)

First level cache: identity map

@Transactional
public void demo() {
    Product a = em.find(Product.class, 1L);                     // SQL
    Product b = em.find(Product.class, 1L);                     // no SQL: same object from the persistence context
    Product c = em.createQuery("select p from Product p where p.id = 1", Product.class).getSingleResult();
                                                                // SQL runs (queries always hit the database) but the row maps to the SAME object a
    assert a == b && b == c;                                    // one row = one Java object per persistence context
}

Important consequence: after a query returns a row that is already managed, Hibernate keeps the object it already has and ignores the fresh column values. If another transaction changed the row, you still see your loaded snapshot (repeatable read at object level). Use em.refresh(entity) to reload.

Second level cache setup (JCache with Ehcache)

<dependency><groupId>org.hibernate.orm</groupId><artifactId>hibernate-jcache</artifactId></dependency>
<dependency><groupId>org.ehcache</groupId><artifactId>ehcache</artifactId><classifier>jakarta</classifier></dependency>
spring:
  jpa:
    properties:
      hibernate:
        cache:
          use_second_level_cache: true
          use_query_cache: false
          region.factory_class: jcache
        javax.cache.provider: org.ehcache.jsr107.EhcacheCachingProvider
        javax.cache.uri: classpath:ehcache.xml
      jakarta.persistence.sharedCache.mode: ENABLE_SELECTIVE      # only entities marked @Cacheable
@Entity
@Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE, region = "countries")
public class Country {
    @Id private String code;
    private String name;

    @OneToMany(mappedBy = "country")
    @org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)     // a collection cache stores only the ids of the elements
    private Set<City> cities = new HashSet<>();
}
Concurrency strategyBehaviorUse for
READ_ONLYNever changes. Fastest. Updates throw an errorReference data
NONSTRICT_READ_WRITEUpdates evict entries after commit. Small stale windowRarely changing data
READ_WRITESoft locks during updates: consistent readsData that changes sometimes (default choice)
TRANSACTIONALFull JTA transactionsSpecial providers

What is actually stored: dehydrated state

em.find(Country.class, "IN")
   1. first level: miss
   2. second level lookup key = Country#IN in region countries
        hit  ─► the cached entry is a "dehydrated" array of column values [name="India", ...]  ─► a NEW Country object is built from it (no SQL)
        miss ─► SQL ─► entity built ─► its state is stored in the second level cache
Relations are stored as ids. Loading a cached Order still needs the customer: from the cache if Customer is cached too, else SQL.

Query cache

@QueryHints(@QueryHint(name = "org.hibernate.cacheable", value = "true"))
List<Country> findByRegion(String region);
// Cached: the list of ids + the parameters. Hit rate is good only when the tables rarely change,
// because any insert, update or delete on a table used by the query invalidates ALL cached results for that table.

Should you use it?

UseDo not use
Read mostly reference data (countries, currencies, settings)Data that changes often (orders, balances)
Single application writing the tables through HibernateOther systems, triggers or bulk SQL also change the data (stale cache)
A measured hot spotBy default 'to be faster' without measurements
Cluster with a distributed provider (Hazelcast, Infinispan, Redis-based)Multiple instances with local caches and no invalidation (each node sees different data)
  • A Spring @Cacheable on a service method that returns a DTO is often simpler, explicit and safer than the Hibernate second level cache.
  • Monitor hit ratios: hibernate.generate_statistics and stats.getSecondLevelCacheHitCount().
  • Remember bulk JPQL updates and native SQL bypass the cache: evict regions manually (emf.getCache().evictAll()).
emf.getCache().evict(Country.class, "IN");           // one entity
emf.getCache().evict(Country.class);                  // whole region
emf.getCache().evictAll();
em.refresh(country);                                  // bypass and reload one entity in the current persistence context

Common mistake: Enabling the second level cache for frequently changing entities or when other systems write to the same tables. Users then read stale data, and the invalidation cost can exceed the gain. Cache only read-mostly reference data, after measuring.

Interview questions

Is the first level cache optional?

No. It is the persistence context and JPA cannot work without it. It lives for one EntityManager (usually one transaction).

Why do I not see fresh values from the database in the same transaction?

The row maps to an entity that is already in the persistence context, and Hibernate keeps the loaded instance. Call em.refresh(entity) or start a new transaction.

Hibernate second level cache or Spring Cache?

Spring Cache is explicit, works on any result and is easy to reason about. Second level cache is transparent for em.find but needs care for invalidation. Start with Spring Cache for hot read paths.
