JPA Relationships and the N+1 Problem

Relationships connect entities. Wrong fetch settings are the most common cause of slow Spring Boot applications, so understand lazy loading and the N+1 problem well.

One-to-many and many-to-one

@Entity
public class Customer {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderEntity> orders = new ArrayList<>();

    public void addOrder(OrderEntity order) {          // keep both sides in sync
        orders.add(order);
        order.setCustomer(this);
    }
    public void removeOrder(OrderEntity order) {
        orders.remove(order);
        order.setCustomer(null);
    }
}

@Entity
@Table(name = "orders")
public class OrderEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String item;

    @ManyToOne(fetch = FetchType.LAZY)                 // always set LAZY explicitly
    @JoinColumn(name = "customer_id")                  // the foreign key column (owning side)
    private Customer customer;

    public void setCustomer(Customer customer) { this.customer = customer; }
}

Many-to-many

@Entity
public class Student {
    @Id @GeneratedValue private Long id;

    @ManyToMany
    @JoinTable(name = "student_course",
               joinColumns = @JoinColumn(name = "student_id"),
               inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set<Course> courses = new HashSet<>();
}
@Entity
public class Course {
    @Id @GeneratedValue private Long id;
    @ManyToMany(mappedBy = "courses")
    private Set<Student> students = new HashSet<>();
}
Cascade typeEffect
PERSISTSaving the parent saves the children
MERGEMerging the parent merges the children
REMOVEDeleting the parent deletes the children
ALLAll of the above
orphanRemoval=trueDeletes a child removed from the parent collection
Fetch typeDefault forMeaning
LAZY@OneToMany, @ManyToManyLoaded only when you access it
EAGER@ManyToOne, @OneToOneLoaded together with the owner

Recommendation: make every association LAZY, and load data explicitly (join fetch or entity graph) when a use case needs it.

The N+1 problem

You load 1 list of 100 customers (1 query). Then for each customer you touch customer.getOrders(), and Hibernate runs one more query per customer (100 queries). Total: 1 + 100 = 101 queries.

select * from customer;                       ← 1 query
select * from orders where customer_id = 1;    ← N queries, one for each customer
select * from orders where customer_id = 2;
select * from orders where customer_id = 3;
...                                            enable spring.jpa.show-sql=true to see them

Fixes

public interface CustomerRepository extends JpaRepository<Customer, Long> {

    // 1. JOIN FETCH: one query with a join
    @Query("select distinct c from Customer c join fetch c.orders")
    List<Customer> findAllWithOrders();

    // 2. Entity graph: same effect, no JPQL
    @EntityGraph(attributePaths = "orders")
    List<Customer> findByNameStartingWith(String prefix);
}
# 3. Batch fetching: load lazy collections in groups (1 query for 50 customers)
spring.jpa.properties.hibernate.default_batch_fetch_size=50
# 4. Do not keep the session open during the view rendering
spring.jpa.open-in-view=false
  • 4. Use DTO projections when you only need a few columns.
  • Do not JOIN FETCH two collections in one query. It creates a huge cartesian product and Hibernate may fail with MultipleBagFetchException.

LazyInitializationException

It happens when you touch a lazy field after the transaction (session) is closed, typically in the controller. Fix it by loading the data inside the service method (join fetch, entity graph) and returning a DTO. Do not fix it by making everything EAGER.

Common mistake: Making associations EAGER to avoid LazyInitializationException. This loads far more data than needed and creates N+1 problems everywhere. Keep LAZY and fetch what each use case needs.

Interview questions

What does mappedBy mean?

It marks the inverse (non-owning) side of the relationship. The other side, with @JoinColumn, owns the foreign key.

Why should I avoid returning entities from REST controllers?

Lazy fields can throw exceptions, bidirectional relations cause infinite JSON recursion, and you expose internal structure. Use DTOs.

What is open-in-view?

A Spring Boot default that keeps the JPA session open until the response is written. It hides lazy loading problems and holds connections longer, so many teams switch it off.
