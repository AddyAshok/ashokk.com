Packaging, Docker and Deployment

Spring Boot builds a single executable jar. Put it in a container, pass configuration through environment variables, and add health probes and graceful shutdown, and it is ready for Docker or Kubernetes.

The executable (fat) jar

./mvnw clean package -DskipTests
java -jar target/shop-0.0.1-SNAPSHOT.jar
java -jar target/shop-0.0.1-SNAPSHOT.jar --server.port=9000 --spring.profiles.active=prod

The spring-boot-maven-plugin repackages your classes and all dependencies into one jar with an embedded Tomcat, so you only need Java on the server.

Simple Dockerfile

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/shop-0.0.1-SNAPSHOT.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]

Multi-stage build with layers (smaller, faster rebuilds)

FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q clean package -DskipTests
RUN java -Djarmode=tools -jar target/*.jar extract --layers --destination /extracted

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /extracted/dependencies/ ./
COPY --from=build /extracted/spring-boot-loader/ ./
COPY --from=build /extracted/snapshot-dependencies/ ./
COPY --from=build /extracted/application/ ./
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]

Layers put rarely changing dependencies in one Docker layer and your code in another, so a small code change rebuilds only a tiny layer. The layer extraction command is java -Djarmode=tools in Boot 3.3 and newer (older versions used -Djarmode=layertools). Check the reference of your version.

Build an image without a Dockerfile (Buildpacks)

./mvnw spring-boot:build-image -Dspring-boot.build-image.imageName=shop:1.0
docker run -p 8080:8080 -e SPRING_PROFILES_ACTIVE=prod shop:1.0

docker-compose with PostgreSQL

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: shop
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
  app:
    image: shop:1.0
    ports: ["8080:8080"]
    depends_on: [db]
    environment:
      SPRING_PROFILES_ACTIVE: prod
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/shop
      SPRING_DATASOURCE_USERNAME: app
      SPRING_DATASOURCE_PASSWORD: secret

Environment variables override properties because of relaxed binding: SPRING_DATASOURCE_URL becomes spring.datasource.url.

Kubernetes probes and graceful shutdown

server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s
management.endpoint.health.probes.enabled=true
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  initialDelaySeconds: 20
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }

Graceful shutdown lets running requests finish before the application stops, so a rolling update does not cut users off.

Performance options

  • Virtual threads (Java 21+): spring.threads.virtual.enabled=true lets blocking code scale to many concurrent requests.
  • GraalVM native image: ./mvnw -Pnative native:compile gives very fast startup and low memory, but a slower build and some limits with reflection.
  • Set the JVM memory for containers with -XX:MaxRAMPercentage instead of a fixed -Xmx.
  • Lazy initialization (spring.main.lazy-initialization=true) speeds up startup but moves errors to the first use.

Common mistake: Baking passwords and environment-specific URLs into the image. Build one image and inject configuration through environment variables or secrets at runtime.

Interview questions

Jar or WAR?

Use the executable jar for almost every new project. Use WAR only if you must deploy into an existing external application server.

How do I reduce the image size?

Use a JRE base image, the layered jar, and multi-stage builds. jlink or native images reduce it further.

Why does my container get OOM killed?

The JVM may size its heap from the host memory. Set a container memory limit and use -XX:MaxRAMPercentage so the JVM respects it.
