Bean Lifecycle and Scopes

Every bean goes through a fixed life: it is created, filled with dependencies, initialized, used and finally destroyed. You can run your own code at these points. Scope decides how many instances exist.

Bean lifecycle

1. Instantiate the bean (constructor)
2. Inject dependencies
3. Aware callbacks (BeanNameAware, ApplicationContextAware ...)
4. BeanPostProcessor.postProcessBeforeInitialization
5. @PostConstruct  →  InitializingBean.afterPropertiesSet()  →  custom init-method
6. BeanPostProcessor.postProcessAfterInitialization   (proxies for @Transactional, @Async are created here)
7. ───── bean is ready and used ─────
8. @PreDestroy  →  DisposableBean.destroy()  →  custom destroy-method  (on shutdown)
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Component;

@Component
public class CacheWarmer {

    public CacheWarmer() { System.out.println("1. constructor"); }

    @PostConstruct
    public void init() { System.out.println("2. @PostConstruct: load data"); }

    @PreDestroy
    public void cleanup() { System.out.println("3. @PreDestroy: release resources"); }
}

Scopes

ScopeInstancesNotes
singleton (default)One per containerShared by all. Must be thread-safe (no changing fields)
prototypeNew one for each injection or getBean callSpring does not call @PreDestroy for it
requestOne per HTTP requestWeb apps only
sessionOne per HTTP sessionWeb apps only
applicationOne per ServletContextWeb apps only
@Component
@Scope("prototype")
public class ShoppingCart { }

@Service
public class CartFactory {
    private final ObjectProvider<ShoppingCart> cartProvider;

    public CartFactory(ObjectProvider<ShoppingCart> cartProvider) {
        this.cartProvider = cartProvider;
    }

    public ShoppingCart newCart() {
        return cartProvider.getObject();      // a NEW cart each time
    }
}

Tip: If you inject a prototype bean directly into a singleton, the singleton gets only ONE instance when it is created. Use ObjectProvider (or a scoped proxy) to get a new instance each time.

@Bean methods and @Configuration

@Configuration(proxyBeanMethods = false)     // faster startup when @Bean methods do not call each other
public class AppConfig {

    @Bean
    public Clock clock() {
        return Clock.systemUTC();
    }

    @Bean(initMethod = "start", destroyMethod = "stop")
    public Scheduler scheduler(Clock clock) {
        return new Scheduler(clock);
    }
}

Run code when the application starts

@Component
public class StartupRunner implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        System.out.println("Application started with args: " + args.getOptionNames());
    }
}

@Component
public class ReadyListener {
    @EventListener(ApplicationReadyEvent.class)
    public void onReady() { System.out.println("Ready to accept requests"); }
}

Common mistake: Keeping user-specific state in fields of a singleton bean (for example the current user name). All requests share the same instance, so data mixes between users. Keep singletons stateless.

Interview questions

Is a Spring singleton the same as the singleton design pattern?

No. A Spring singleton is one instance per container. The design pattern is one instance per JVM/class loader.

When should I use @PostConstruct?

For initialization that needs injected dependencies, for example loading data into a cache. The constructor runs before injection is finished.

What is the difference between @Bean and @Component?

@Component is put on your own class and found by scanning. @Bean is a method in a configuration class, useful for third-party classes you cannot annotate.
