Transactions with @Transactional

A transaction groups database operations so that they all succeed or all fail together. Spring makes this easy with @Transactional, but you must understand how the proxy works to avoid silent mistakes.

Basic example: money transfer

@Service
public class TransferService {

    private final AccountRepository accounts;

    public TransferService(AccountRepository accounts) { this.accounts = accounts; }

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accounts.findById(fromId).orElseThrow();
        Account to = accounts.findById(toId).orElseThrow();
        from.withdraw(amount);                      // throws if balance is too low
        to.deposit(amount);
        // commit happens when the method ends normally.
        // A RuntimeException rolls BOTH changes back.
    }
}

Spring wraps the service bean in a proxy. Before your method it opens a transaction, and after it commits (or rolls back on exception). Entity changes made inside the transaction are saved automatically at commit (dirty checking), even without calling save().

Propagation: what if a transactional method calls another one?

PropagationBehavior
REQUIRED (default)Join the current transaction, or create one if none exists
REQUIRES_NEWAlways start a new transaction and suspend the current one
SUPPORTSUse a transaction if one exists, otherwise run without
NOT_SUPPORTEDRun without a transaction (suspend the current one)
MANDATORYMust run inside a transaction, otherwise throw an exception
NEVERMust run without a transaction, otherwise throw an exception
NESTEDNested transaction with a savepoint
@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)   // saved even if the caller rolls back
    public void log(String message) { /* save audit row */ }
}

Isolation levels

IsolationDirty readNon-repeatable readPhantom read
READ_UNCOMMITTEDPossiblePossiblePossible
READ_COMMITTEDPreventedPossiblePossible
REPEATABLE_READPreventedPreventedPossible
SERIALIZABLEPreventedPreventedPrevented

The default is the database default (READ_COMMITTED in PostgreSQL and Oracle, REPEATABLE_READ in MySQL InnoDB). Higher isolation gives more safety but less concurrency.

Rollback rules

  • By default a transaction rolls back on RuntimeException and Error only.
  • Checked exceptions (for example IOException) do NOT roll back by default.
  • Use @Transactional(rollbackFor = Exception.class) to roll back on checked exceptions too.
  • @Transactional(readOnly = true) is a hint for queries. It can improve performance and avoids accidental writes.

Common pitfalls

@Service
public class OrderService {

    public void placeOrder(Order o) {
        saveOrder(o);                     // PITFALL 1: self-invocation, no proxy, NO transaction!
    }

    @Transactional
    public void saveOrder(Order o) { /* ... */ }

    @Transactional
    public void wrong() {
        try {
            riskyDatabaseCall();
        } catch (Exception e) {
            // PITFALL 2: swallowed exception. The transaction still commits
            // (or is marked rollback-only by an inner call and fails at commit).
        }
    }

    @Transactional
    private void hidden() { }             // PITFALL 3: private methods are not proxied
}
  • Fix for pitfall 1: move the transactional method to another bean, or put @Transactional on the outer method.
  • Do not keep transactions open during slow work such as HTTP calls. Long transactions hold database connections and locks.
  • A new thread (@Async) does not share the transaction of the caller.
  • Put @Transactional on the service layer, not on controllers or repositories.

Programmatic transaction

@Service
public class ReportService {
    private final TransactionTemplate tx;
    public ReportService(PlatformTransactionManager manager) { this.tx = new TransactionTemplate(manager); }

    public void run() {
        tx.executeWithoutResult(status -> {
            // database work
            // status.setRollbackOnly();   // roll back manually
        });
    }
}

Common mistake: Calling a @Transactional method from another method of the same class. The proxy is bypassed, so no transaction is started. Move it to a separate bean.

Interview questions

What is the default rollback behavior?

Rollback for RuntimeException and Error. Checked exceptions commit unless you set rollbackFor.

What is the difference between REQUIRED and REQUIRES_NEW?

REQUIRED joins the existing transaction. REQUIRES_NEW suspends it and creates a separate one that commits or rolls back independently.

Why does @Transactional not work on private methods?

The proxy can only intercept calls that come from outside through public (or protected) methods.
